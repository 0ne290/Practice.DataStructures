# Правила работы с репозиторием

Источник требований: `docs/specification.md` и связанный исходный документ.

- Для всех коллекций разделять профиль API (список, стек, очередь, дек),
  организацию хранения (на массиве или на связанных узлах; односвязность
  и двусвязность) и политику вместимости.
  Обязательные определения и имена: `docs/collection-semantics.md`.
  «Классический» и «традиционный» — синонимы одного зафиксированного профиля.
  Способ хранения не определяет FIFO/LIFO и набор операций; расширения API
  и сложность указывать явно. «Линейный» не означает «на массиве».
  Встроенный массив C# `T[]` — базовое хранилище фиксированной длины,
  а не отдельная реализуемая коллекция; собственный фиксированный массив
  не создавать. Коллекции на массивах строить на `T[]` непосредственно
  или через собственные коллекции; связные — на узлах и ссылках.
  Словарь не изменяет принятые реализации Core задним числом.
  Имена типов, файлов, тестовых тем и XML-комментарии согласовывать со словарём.
  План упражнений задаётся в `docs/specification.md`, целевой профиль двух
  списков на массивах — в `docs/array-list-profiles.md`. Целевой API отличать
  от уже реализованного; согласование профиля не означает начало реализации.

- Дисциплина: структуры данных и алгоритмы. Один solution и ровно два проекта:
  `Practice.DataStructures.Core` и `Practice.DataStructures.Tests`.
- Core — библиотека. Не добавлять Program.cs, Main, консольное меню или третий проект.
- Реализации Core и дизайн публичного API пишет автор практикума самостоятельно.
  Не писать, не дополнять и не исправлять код Core без отдельного явного запроса
  пользователя. Настройка файлов проектов и папок разрешена. После завершения
  обоих этапов ревью нейросеть оформляет XML-комментарии по принятому решению.
- Можно объяснять, проводить ревью, формулировать требования и работать над Tests.
  Порядок работы: академическая постановка задачи и лабораторный полигон →
  самостоятельная реализация автора → ревью функциональной корректности и
  надёжности с исправлениями автора → отдельное ревью архитектуры, кода и API
  с исправлениями автора → XML-комментарии, тесты и полноценная демонстрация.
  Не раскрывать заранее инварианты, граничные случаи, ветки решения и сигнатуры
  без запроса автора. До окончания функционального ревью не оценивать форму.
  Актуальные намеренные решения автора имеют приоритет над исходной спецификацией.
  Подробности и границы адаптации: `docs/testing.md`.
- Названия типов и публичных членов, XML-комментарии и поведение согласовывать
  со словарём по правилу самодокументируемости в `docs/collection-semantics.md`.
  Проверку согласованности имени, словаря, API и поведения проводить на втором
  этапе ревью; итоговые XML-комментарии оформлять и сверять после обоих этапов.
- Условия (делегаты-предикаты в C#) применять к операциям, которые по своей
  природе последовательно проверяют элементы. В упорядоченных коллекциях
  условию доступны элемент и его позиция. Сохранять эффективные операции
  прямого доступа; не заменять их перебором. Подробности: `docs/specification.md`.
- Внутри учебных структур не использовать коллекции BCL как хранилище.
  Разрешены массивы, примитивы и runtime; эталонные коллекции допустимы в Tests.
- Общие контрактные тесты применять к альтернативным реализациям;
  проверки специфических инвариантов держать отдельно.
- Обычные тесты: xUnit v3, AAA, Fact/Theory, осмысленные имена, граничные случаи,
  ошибки и детерминированность. Вывод не заменяет Assert.
- Лабораторные сценарии: `Category=Laboratory`; измерения: `Category=Performance`.
  На каждую задачу сразу создавать ровно один `[Fact]` категории Laboratory
  как полигон автора. До завершения обоих этапов ревью его содержимым управляет
  автор; после них нейросеть заменяет его полноценной демонстрацией и пишет тесты.
  При расширении задачи обновлять существующий сценарий. Правила: `docs/testing.md`.
  Сценарии запускаются явно. В демонстрациях по умолчанию выбирать новый случайный
  seed, записывать seed и параметры и поддерживать повтор по заданному seed.
  Обычные тесты оставлять детерминированными; в измерениях фиксировать seed.
  Для замеров: прогрев, повторения, одинаковые входы, проверка корректности до
  замера; генерацию данных исключать из измеряемого участка.
- Не добавлять абсолютные ограничения времени в проверки корректности.
- Перед работой, зависящей от окружения или сторонних библиотек, читать
  `environment.local.json`.
  Если файла, раздела или нужного поля нет, исследовать только недостающие
  сведения на текущем устройстве и сохранить их в этом локальном кэше.
  Правила проверки актуальности, выбора API и команды: `docs/environment.md`.
- Версии инструментов окружения не закреплять; обновлениями управляет пользователь.
  Целевая платформа и NuGet-зависимости задаются проектом; при обновлении
  пакетов обновлять packages.lock.json.
- Перед завершением изменений запускать команды проверки из README.md.
- Для тестового кода применять `tests/CODE_CONVENTIONS.md`.
- Папки, helpers, зависимости и настройки добавлять для текущей задачи,
  без пустых заготовок и инфраструктуры на будущее.
