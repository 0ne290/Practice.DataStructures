# Правила работы с репозиторием

Источник требований: `docs/specification.md` и связанный исходный документ.

- Дисциплина: структуры данных и алгоритмы. Один solution и ровно два проекта:
  `Practice.DataStructures.Core` и `Practice.DataStructures.Tests`.
- Core — библиотека. Не добавлять Program.cs, Main, консольное меню или третий проект.
- Реализации Core и их публичные контракты пишет автор практикума самостоятельно.
  Не писать, не дополнять и не исправлять код Core без отдельного явного запроса
  пользователя. Настройка файлов проектов и папок разрешена.
- Можно объяснять, проводить ревью, формулировать требования и работать над Tests.
  Пока API не определён, не придумывать за автора интерфейсы и сигнатуры.
  Порядок работы: автор задаёт спецификацию API → нейросеть пишет тесты и
  лабораторный сценарий → автор пишет реализацию → нейросеть сверяет принятые
  автором технические решения и точечно адаптирует Tests.
  Актуальные намеренные решения автора имеют приоритет над исходной спецификацией.
  Подробности и границы адаптации: `docs/testing.md`.
- Внутри учебных структур не использовать коллекции BCL как хранилище.
  Разрешены массивы, примитивы и runtime; эталонные коллекции допустимы в Tests.
- Общие контрактные тесты применять к альтернативным реализациям;
  проверки специфических инвариантов держать отдельно.
- Обычные тесты: xUnit v3, AAA, Fact/Theory, осмысленные имена, граничные случаи,
  ошибки и детерминированность. Вывод не заменяет Assert.
- Лабораторные сценарии: `Category=Laboratory`; измерения: `Category=Performance`.
  На каждую задачу автоматически готовить ровно один демонстрационный `[Fact]`
  вместе с обычными тестами, до реализации Core, без отдельного напоминания.
  При расширении задачи обновлять существующий сценарий. Правила: `docs/testing.md`.
  Сценарии запускаются явно. В демонстрациях по умолчанию выбирать новый случайный
  seed, записывать seed и параметры и поддерживать повтор по заданному seed.
  Обычные тесты оставлять детерминированными; в измерениях фиксировать seed.
  Для замеров: прогрев, повторения, одинаковые входы, проверка корректности до
  замера; генерацию данных исключать из измеряемого участка.
- Не добавлять абсолютные ограничения времени в проверки корректности.
- Перед работой, зависящей от окружения или сторонних библиотек, читать
  `environment.local.json`.
  Если файла, раздела или нужного поля нет, исследовать только недостающие
  сведения на текущем устройстве и сохранить их в этом локальном кэше.
  Правила проверки актуальности, выбора API и команды: `docs/environment.md`.
- Версии инструментов окружения не закреплять; обновлениями управляет пользователь.
  Целевая платформа и NuGet-зависимости задаются проектом; при обновлении
  пакетов обновлять packages.lock.json.
- Перед завершением изменений запускать команды проверки из README.md.
- Для тестового кода применять `tests/CODE_CONVENTIONS.md`.
- Папки, helpers, зависимости и настройки добавлять для текущей задачи,
  без пустых заготовок и инфраструктуры на будущее.
