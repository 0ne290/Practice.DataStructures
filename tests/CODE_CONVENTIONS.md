# Кодовые соглашения тестового проекта

Действуют для C#-кода в `tests/`: тестов, данных, фикстур, эталонов и
лабораторных сценариев. Используются целевая платформа проекта и xUnit v3;
фактическое окружение определяется по [правилам работы с окружением](../docs/environment.md).
Правила проверяемого поведения, AAA и запуска — в
[тестовой лаборатории](../docs/testing.md).

## Написание кода

- Перед изменением изучить ближайший рабочий код и продолжить его соглашения.
  Современный синтаксис и API применять, когда они улучшают ясность или
  безопасность; не переписывать понятный код ради более нового синтаксиса.
- Сохранять nullable reference types. Не отключать диагностики, не использовать
  `!`, `#pragma` или `SuppressMessage` без конкретной обоснованной причины.
- Использовать file-scoped namespace и фигурные скобки для блоков управления.
  `var` уместен при очевидном типе справа; в остальных случаях указывать тип.
- Называть тестовые классы по проверяемому поведению с суффиксом `Tests`,
  методы — `Действие_Условие_ОжидаемыйРезультат` на английском.
  Helpers, эталоны и данные должны иметь предметные имена, раскрывающие роль.
- Оставлять минимальную необходимую видимость: helper одного класса — private,
  вспомогательный тип внутри сборки — internal. Публичная видимость оправдана
  требованиями xUnit к обнаружению тестов и источников данных; не уменьшать её
  механически по подсказке IDE.

## Организация и зависимости

- Группировать код по структуре данных или проверяемому поведению. Данные,
  эталоны и helpers одной темы держать рядом с её тестами, а не разносить по
  глобальным папкам `Helpers`, `Utilities` и `Common`.
- Выносить общий код, когда у нескольких групп действительно одна
  ответственность и причина изменения. Похожих строк недостаточно для новой
  абстракции, универсального builder или базового класса тестов.
- В C#-файле один главный top-level тип с именем файла. Вложенный тип допустим
  как неотделимая часть владельца; самостоятельная ответственность получает
  отдельный тип и файл. Не создавать папку или namespace без текущей нужды.
- Зависимости передавать явно через параметры, конструкторы и фикстуры xUnit.
  Не вводить service locator, DI-контейнер или изменяемое глобальное состояние.
  Тесты не зависят от порядка запуска. Фикстура владеет созданными ресурсами,
  освобождает их и не передаёт изменяемые данные между независимыми сценариями.
- Каждый тест должен показывать проверяемое действие и ожидаемый результат.
  Helper не должен скрывать вызов Core за универсальным сценарием или
  воспроизводить его реализацию в качестве единственного эталона.

## Review и инструменты

- Проверить ближайших владельцев данных, зависимости и потребителей изменённого
  helper или источника данных. Убедиться, что новый сценарий остаётся понятным,
  воспроизводимым и независимым, а ресурс освобождается и при падении Assert.
- Не оставлять предупреждения компилятора, SDK-анализаторов и xUnit-анализаторов.
  Rider inspections обязательны для изменённых C#-файлов: замечания по
  корректности и видимости исправлять, suggestions оценивать по читаемости.
  Неприменённое обоснованное предупреждение назвать в результате работы.
- В Tests используются анализаторы SDK и xUnit, включена проверка стиля при
  сборке. Предупреждения считаются ошибками. Настройки C# и Rider в
  `.editorconfig` ограничены `tests/`.
- Менять соседний код только при необходимости текущей задачи. Правило хранить
  в одном документе; вместо повтора ссылаться на его источник. Не записывать
  историю обсуждений и гипотетические требования.
