# Семантика коллекций практикума

Этот документ задаёт обязательный словарь для постановок, обсуждений, ревью и
тестов всего практикума. Это соглашение проекта: оно не утверждает, что учебники,
языки и библиотеки используют те же слова в единственном значении. Намеренное
решение автора конкретной задачи имеет приоритет; отклонение записывается явно.

## Два независимых уровня

**Уровень API** определяет доступные операции, их наблюдаемое поведение,
логический порядок элементов и способы выбора позиции. Сюда относятся
«массив», «список», «стек», «очередь», «дек» (также «дека»).

**Уровень организации хранения** определяет размещение элементов, связи,
соответствие логических позиций физическим и стоимость операций. Сюда относятся
«линейный», «кольцевой», «связный», «односвязный», «двусвязный».
Способ хранения сам по себе не добавляет и не запрещает публичные операции.

Полное описание коллекции состоит из профиля API, организации хранения и
явных дополнительных свойств: расширяемость, ограничение вместимости,
поведение при заполнении, расширения API и требования к сложности.
Название профиля не задаёт C#-сигнатуры, имена методов или публичность узлов.
Их по-прежнему выбирает автор.

## Организация хранения

| Термин | Значение в практикуме | Чего термин сам по себе не означает |
| --- | --- | --- |
| Линейное хранение | Последовательное размещение в блоке ячеек: логический порядок идёт по физическим позициям без перехода с конца блока в начало | Фиксированную длину, FIFO или конкретный набор операций |
| Кольцевое хранение в блоке | Логическая последовательность может переходить с конца блока в его начало; освободившиеся позиции используются повторно | Циклический публичный индексатор, FIFO, перезапись или автоматический рост |
| Связное хранение | Элементы размещены в узлах, порядок задают связи между ними | API списка, отсутствие индексатора или обязательный перебор для каждой операции |
| Односвязное / двусвязное | Узлы имеют связи в одном / двух направлениях | Разные правила выбора элементов на уровне API |
| Кольцевое связное хранение | Связи узлов замыкают последовательность в кольцо | Бесконечный публичный перебор или отсутствие логического начала |

В этом словаре «линейный» имеет указанное значение хранения. В литературе
«линейная структура» может означать любую последовательность, включая связную;
при таком цитировании нужно пояснить чужое значение. «Кольцевой» и «связный»
совместимы: одно описывает замыкание порядка, другое — способ размещения и связей.
Для слова «кольцевой» всегда указывать носитель, если он не понятен из контекста.

Низкоуровневое разрешённое хранилище C# обозначается буквально `T[]` или
«встроенный массив C#». Это конкретный тип runtime с фиксированной длиной,
а не профиль изменяемого массива практикума.

## «Классический» и «традиционный»

В практикуме это полные синонимы: оба слова ссылаются на базовый профиль API
из таблицы ниже. Если организация не названа, она остаётся неуказанной.
«Классический массив» и «традиционный массив» подразумевают один набор операций;
«классический линейный массив» и «традиционный линейный массив» добавляют к нему
одинаковое требование линейного хранения.

Это зафиксированные рабочие значения распространённых абстракций, а не
утверждение о всеобщем стандарте терминов. Нельзя подменять профиль API
поведением случайно выбранной библиотеки или менять смысл между обсуждениями.
При сравнении с внешним источником указывать конкретный тип и различия.

## Базовые профили API

Для всех профилей предусмотрены количество элементов, проверка пустоты,
очистка и конечный последовательный перебор без удаления элементов.
Элементы сохраняют логический порядок; значения могут повторяться.
Индекс, где он предусмотрен, отсчитывается от нуля и обозначает текущую
логическую позицию существующего элемента в диапазоне `[0, Count)`.
Неявное циклическое оборачивание индексов отсутствует.

| Профиль | Базовые операции сверх общих | Способ выбора позиции и порядок |
| --- | --- | --- |
| Массив | Чтение и замена по индексу; добавление в конец; удаление по индексу с сохранением порядка остальных элементов; поиск первой позиции и проверка наличия по условию | Логический индекс; поиск получает элемент и его позицию; перебор от начала к концу |
| Список | Добавление в начало и конец; чтение и замена выбранного элемента; вставка перед/после выбранной позиции; удаление выбранного элемента; поиск по условию | Позиция задаётся курсором либо другим явно описанным средством; условие получает элемент и позицию; перебор от начала к концу |
| Стек | Добавление, чтение и извлечение с вершины | LIFO; перебор от вершины к основанию |
| Очередь | Добавление в конец, чтение и извлечение из начала | FIFO; перебор от начала к концу |
| Дек / дека | Добавление, чтение и извлечение на обоих концах | Конец операции выбирается явно; перебор от начала к концу |

Это профили требований, а не обязательные интерфейсы C# или перечень уже
реализованных возможностей. Более широкий API может удовлетворять нескольким
профилям. Для стека и очереди как отдельных обёрток практикума оставлять их
ограниченный API: наличие индексатора у внутреннего хранилища не требует
выставлять его наружу. Вместимость характеризует конкретное хранилище;
свойство Capacity не требуется от каждой связной реализации.

### Массив и список: неоднозначность имён

«Массив» без уточнения в постановках коллекций означает **изменяемую
индексируемую последовательность** с операциями из таблицы. Он не ограничивается
чтением/записью фиксированного числа ячеек. Фиксированный массив должен быть
назван явно; добавление и удаление из его контракта исключаются явно.
«Динамический» / «расширяемый» дополнительно означает автоматический рост
вместимости по мере добавления, без потери уже записанных элементов.

«Список» означает последовательность с позиционными операциями вставки и
удаления. Список не обязан храниться в связанных узлах; массив не обязан
храниться в непрерывном блоке. Различие профилей — в обязательных операциях
и средствах адресации. У списка индексатор не подразумевается; у массива
обязателен. Если список предоставляет также индексный доступ, это отмечается
как расширение. Профили могут пересекаться.

Сложность указывается отдельно от функционального контракта. Для линейного
массива ожидаются O(1) чтение/замена по индексу, амортизированное O(1)
добавление в конец при автоматическом росте и O(n) удаление в произвольной
позиции в худшем случае. Для связного массива индексатор сохраняется,
но поиск узла по индексу может занимать O(n). Требование O(1) произвольной
индексации исключает простую цепочку узлов как достаточную реализацию.

В односвязном списке операции перед выбранной позицией могут требовать поиска
предшественника. Односвязность не отменяет операцию API и не обещает O(1).
Автор может выбрать более узкий профиль списка; его ограничения фиксируются
в постановке и принятом контракте, как у уже реализованных списков проекта.

Имена BCL не задают словарь практикума. `List<T>` может служить эталоном
индексируемой последовательности, `LinkedList<T>` — примером списка со связным
хранением. Их названия при использовании BCL остаются исходными.

### Имена типов проекта

В составном имени типа сначала указывается организация хранения, затем профиль
API. Для текущих структур приняты следующие имена:

| Тип | Организация | API и дополнительные свойства |
| --- | --- | --- |
| `LinearArray<T>` | Линейное размещение в `T[]` | Массив с автоматическим ростом вместимости |
| `CircularArray<T>` | Кольцевое размещение в `T[]` | Расширяемый массив; явные расширения задаёт текущая постановка |
| `SinglyLinkedList<T>` | Односвязные узлы | Принятый позиционный API списка |
| `DoublyLinkedList<T>` | Двусвязные узлы | Принятый позиционный API списка |
| `LinearStack<T>` | Линейное хранилище `LinearArray<T>` | Стек |
| `LinkedStack<T>` | Связное хранилище `SinglyLinkedList<T>` | Стек |

`Dynamic` описывает рост, но не различает линейное и кольцевое хранение.
Поэтому прежний `DynamicArray<T>` переименован в `LinearArray<T>`;
его расширяемость сохранена. Прежний `ArrayStack<T>` переименован в
`LinearStack<T>`: слово Array в составном имени больше не используется как
неявный синоним организации хранения. Остальные перечисленные имена уже
соответствуют разделению уровней. Имена файлов, тестовых тем и пространства
имён тестов следуют имени проверяемой структуры; общие тесты стеков остаются
в теме Stack. Исторические ревью используют актуальные имена типов.

В названиях будущих обёрток на кольцевом хранилище использовать
`CircularQueue<T>` и `CircularDeque<T>`, на связном — `LinkedQueue<T>` и
`LinkedDeque<T>`. Эта договорённость не создаёт новые типы заранее.

### Примеры сочетаний с конкретным смыслом

| Выражение | Профиль API | Организация и следствия |
| --- | --- | --- |
| Линейный массив | Массив | Блок ячеек без кольцевого перехода; прямой индексный доступ |
| Связный массив | Массив, включая индексатор и удаление по индексу | Узлы со связями; индексный доступ обычно требует прохода |
| Линейный список | Список, включая позиционные вставки и удаления | Блок ячеек; изменение порядка может требовать сдвигов; стабильность курсоров оговаривается отдельно |
| Связный список | Список | Узлы со связями; односвязность или двусвязность уточняется отдельно |
| Кольцевой массив | Массив | Кольцевое размещение в блоке ячеек; индексатор остаётся ограниченным логическим диапазоном |
| Очередь на кольцевом массиве | Очередь с закрытым внутренним хранилищем | Хранилище — кольцевой массив; обёртка предоставляет FIFO |

Таблица задаёт смысл сочетаний, а не новые обязательные упражнения.
Функциональное совпадение профилей не означает одинаковую организацию памяти
или одинаковую сложность. Например, дек может иметь линейное, кольцевое или
связное хранение, но требование O(1) операций на концах сужает выбор реализации.

## Расширения и политики не выводятся из названия хранения

Добавление в начало, специальное удаление с концов, резервирование, уплотнение,
обратный обход, циклический доступ и перезапись при заполнении — отдельные
возможности. Они обязательны только там, где следуют из выбранного профиля
API или явно указаны в задаче. Политика заполнения фиксируется отдельно:
рост, отказ, ожидание или перезапись. Для текущего расширяемого массива выбран
рост без перезаписи. Слова «кольцевой буфер» сами по себе не определяют политику.

Ошибки аргументов, поведение пустых операций, инвалидирование курсоров и
перечислителей, точная стратегия роста и имена методов оформляются в принятом
контракте конкретной реализации. Их нельзя выводить только из слова
«традиционный» или приписывать всем коллекциям по аналогии с одним классом.
Публичный циклический доступ, если он понадобится, описывается отдельно от
физического перехода через конец хранилища.

## Применение в задачах и ревью

Каждая новая постановка называет профиль API и организацию хранения раздельно,
перечисляет расширения и отклонения, задаёт нужные ограничения сложности.
При первом использовании нового неоднозначного термина сначала добавлять его
определение сюда. Не требовать новые операции только на основании способа хранения.

Общий контракт проверяет одинаковое поведение альтернативных реализаций;
проверки организации хранения и её специфических инвариантов остаются отдельными.
Ограничения сложности относятся к явно указанной реализации или задаче.
Подмена индексного API последовательным поиском по условию не допускается.

Словарь не меняет задним числом принятый API готовых структур. Исторические
ревью описывают фактически принятое решение. Отличия от базового профиля
фиксируются как осознанные варианты; новые функции Core и тесты появляются
только в соответствующей задаче с обычными двумя этапами ревью.
