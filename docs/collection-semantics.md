# Семантика коллекций практикума

Этот документ задаёт общий словарь для постановок, обсуждений, ревью и тестов.
Он описывает абстракции коллекций и способы их реализации, а не только перечень
классов Core. Намеренное решение автора конкретной задачи имеет приоритет;
отклонения от базового профиля фиксируются явно.

## Абстракция, организация хранения и вместимость

**Абстракция и профиль API** определяют операции, наблюдаемое поведение,
логический порядок и способы выбора позиции: список, стек, очередь, дек.

**Организация хранения** определяет размещение элементов и связи между ними:
на массиве или на связанных узлах. Для узлов уточняется односвязность или
двусвязность. Способ хранения сам по себе не задаёт FIFO/LIFO и публичные операции.

**Политика вместимости** определяет ограничения хранилища и поведение при
заполнении. Фиксированная вместимость и автоматическое расширение указываются
явно. Фиксированная вместимость списка не означает фиксированное количество
элементов: оно может меняться в пределах этой вместимости.

Требования к сложности и расширения API задаются отдельно. Название абстракции
не определяет C#-сигнатуры, имена методов и публичность узлов; их выбирает автор.

## Массив как базовое хранилище

Встроенный массив C# (`T[]`) — стандартная базовая фундаментальная структура
данных фиксированной длины, предоставляемая языком и средой выполнения.
Значения его элементов можно заменять; количество позиций созданного массива
не меняется. Отдельная собственная реализация фиксированного массива
в практикуме не предусматривается.

Все коллекции проекта с хранением на массивах строятся на `T[]` — непосредственно
или через собственные коллекции проекта. Расширение такой коллекции не меняет
длину существующего массива: используется другое хранилище большей длины.
Коллекции на связанных узлах строятся на узлах и ссылках и не обязаны использовать
массивы. Коллекции BCL как внутреннее хранилище учебных структур запрещены.

Массив не выделяется в отдельный профиль API реализуемых коллекций.
Слово «массив» обозначает `T[]`, в том числе входные данные алгоритмов;
выражение «на массиве» обозначает организацию хранения собственной коллекции.
Термин «динамический массив» встречается в литературе для расширяемого списка
на массиве; в документах проекта используется название «список на массиве».

## Организация хранения и слово «линейный»

| Термин | Значение в практикуме | Чего термин сам по себе не означает |
| --- | --- | --- |
| Хранение на массиве | Элементы размещены в ячейках `T[]`; соответствие логических позиций ячейкам задаёт реализация | Фиксированное количество элементов коллекции, автоматический рост или конкретный API |
| Кольцевая организация массива | Логическая последовательность может продолжаться через конец массива к его началу | Отдельную абстракцию коллекции, FIFO/LIFO или оборачивание публичных индексов |
| Хранение на связанных узлах | Элементы размещены в узлах, порядок задают ссылки между ними | Только API списка, отсутствие индексатора или перебор для каждой операции |
| Односвязные узлы | Связи позволяют двигаться по последовательности в одном направлении | Конкретный публичный API и одинаковую стоимость всех операций |
| Двусвязные узлы | Связи позволяют двигаться в обоих направлениях | Автоматическое наличие обратного публичного обхода или курсоров |

«Линейная структура данных» — общее теоретическое обозначение последовательной
организации элементов, применимое в том числе к связным спискам. Слово
«линейный» не используется как синоним хранения на массиве и как признак,
отличающий его от связного хранения. В описаниях реализаций следует писать
«на массиве» или «на связанных узлах».

## «Классический» и «традиционный»

В практикуме это синонимы: оба слова обозначают базовый профиль API из таблицы
ниже. Если организация хранения не названа, она остаётся неуказанной.
Это рабочие определения проекта, а не утверждение о единственном словаре
всех учебников и библиотек. При сравнении с внешним источником нужно указывать
конкретный тип и различия его контракта.

## Базовые профили API

Для всех профилей предусмотрены количество элементов, проверка пустоты,
очистка и конечный последовательный перебор без удаления элементов.
Значения могут повторяться. Индекс, где он предусмотрен, отсчитывается от нуля
и обозначает текущую логическую позицию в диапазоне `[0, Count)`.

| Профиль | Базовые операции сверх общих | Способ выбора позиции и порядок |
| --- | --- | --- |
| Список | Чтение и замена выбранного элемента; вставка и удаление элементов с сохранением порядка остальных; поиск по условию | Индекс, курсор или другое явно описанное средство; условие получает элемент и его позицию; перебор от начала к концу |
| Стек | Добавление, чтение и извлечение с вершины | LIFO; перебор от вершины к основанию |
| Очередь | Добавление в конец, чтение и извлечение из начала | FIFO; перебор от начала к концу |
| Дек / дека | Добавление, чтение и извлечение на обоих концах | Конец операции выбирается явно; перебор от начала к концу |

Список — упорядоченная последовательность с операциями доступа, вставки
и удаления. Конкретные доступные позиции вставки и удаления, средства адресации
и стоимость операций фиксируются в профиле задачи и принятом контракте.
Индексатор и курсоры не обязательны для каждого списка. Поиск может возвращать
позицию, значение или курсор согласно контракту конкретной реализации.

Таблица не предписывает обязательные интерфейсы C# и не добавляет операции
готовым структурам. Точный состав API фиксируется в профиле задачи и принятом
контракте. Наличие индексатора у внутреннего списка не требует открывать его
у стека или очереди.

## Названия и принятые варианты

Префикс `Array` обозначает хранение на массиве, `Linked` — на связанных узлах.
`SinglyLinked` и `DoublyLinked` уточняют связи узлов. Рост вместимости указывается
в контракте, а не выводится из префикса.
Префикс `Circular` у `CircularArrayList<T>` уточняет организацию хранения
на массиве; профиль API остаётся индексируемым списком.

| Имя структуры в документах | Организация хранения | Принятый профиль или назначение |
| --- | --- | --- |
| `ArrayList<T>` | `T[]` | Индексируемый список |
| `CircularArrayList<T>` | `T[]` с кольцевой организацией | Индексируемый список; целевой профиль описан отдельно |
| `SinglyLinkedList<T>` | Односвязные узлы | Принятые операции над значениями и отдельное курсорное API |
| `DoublyLinkedList<T>` | Двусвязные узлы | Принятый позиционный API с курсорами |
| `ArrayStack<T>` | Собственный `ArrayList<T>` | Стек |
| `LinkedStack<T>` | Собственный `SinglyLinkedList<T>` | Стек |
| `ArrayQueue<T>` / `LinkedQueue<T>` | На массиве / на связанных узлах | Альтернативные реализации очереди |
| `ArrayDeque<T>` / `LinkedDeque<T>` | На массиве / на связанных узлах | Альтернативные реализации дека |

Текущий статус, целевой API и сложность двух списков определены в
[профилях списков на массивах](array-list-profiles.md), рекомендованный маршрут —
в [спецификации](specification.md#инженерное-расширение-раздела-4-два-подхода-к-реализации-структур-данных).
Перечень имён не означает, что все структуры уже реализованы.
Имена типов и их файлов совпадают; правила тестовых тем задаются в
[тестовой лаборатории](testing.md). `Capacity` не является обязательным
свойством всех коллекций.

## Самодокументируемость имён и XML-комментариев

Названия типов и публичных членов, XML-комментарии и фактическое поведение
должны быть согласованы со словарём проекта и принятым контрактом реализации.
Название типа должно однозначно обозначать абстракцию коллекции и организацию
хранения. Существенные особенности, меняющие ожидаемый контракт, отражаются
в названии либо явно выделяются в документации типа. Название не должно
обещать отсутствующие возможности; названия публичных членов должны
соответствовать назначению и наблюдаемому поведению операций.

По имени типа должно быть понятно, к какому виду относится структура и как
организовано её хранение. Полный API не требуется кодировать в имени:
публичные члены и XML-комментарии вместе должны позволять понять весь контракт
без чтения реализации. Например, `ArrayList<T>` обозначает список на массиве,
а доступные позиции вставки и политика расширения раскрываются в его контракте.

XML-комментарии типа описывают назначение коллекции, поддерживаемые операции,
порядок элементов, средства адресации, политику вместимости, сложность
и ограничения. Комментарии публичных членов уточняют их поведение, параметры,
результаты, ошибки и влияние на курсоры и перечислители, где это применимо.
Используются термины словаря; описания не должны противоречить друг другу
и фактическому поведению или приписывать реализации неподдерживаемые операции.

Согласованность имени, словаря, публичного API и поведения проверяется на втором
этапе ревью — архитектуры, кода и API. Уже имеющиеся XML-комментарии проверяются
на соответствие тому же контракту. Отсутствие итоговых XML-комментариев до этого
этапа не является нарушением: их оформление и итоговая сверка выполняются
после завершения обоих этапов ревью по принятому решению.

## Расширения и конкретные контракты

Вставка в произвольную позицию, резервирование вместимости, уплотнение,
обратный обход и курсоры обязательны только при явном указании в задаче
или принятом контракте. Политика вместимости описывается отдельно.

Ошибки аргументов, поведение пустых операций, инвалидирование курсоров
и перечислителей, точная стратегия роста и имена методов оформляются
в контракте реализации. Их нельзя выводить из слова «традиционный»
или приписывать всем коллекциям по аналогии с одним классом.

## Применение в задачах и ревью

Один класс может реализовывать абстракцию и одновременно служить хранилищем
для другой коллекции. Совпадение API не доказывает существование разных АТД.

Каждая постановка отдельно называет профиль API, организацию хранения,
политику вместимости, расширения и ограничения сложности. Не требовать новых
операций только на основании способа хранения. Эффективные операции прямого
доступа сохраняются; заменять их последовательным поиском по условию нельзя.

Общий контракт проверяет одинаковое поведение альтернативных реализаций;
проверки специфических инвариантов хранения остаются отдельными.
Совпадение абстракции не требует одинаковых средств адресации и полного API
у всех списков. Общие тесты применяются только к действительно общему контракту.

Словарь не меняет принятый API готовых структур задним числом. Ревью описывают
фактически принятое поведение с использованием согласованных названий.
Новые функции Core и соответствующие тесты появляются в отдельной задаче
с обычными двумя этапами ревью.
