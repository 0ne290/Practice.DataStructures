# Бинарное дерево поиска: первая задача

Базовая часть [СА-03](specification.md#са-03-бинарное-дерево-поиска-и-авл-дерево).
Цель — изучить хранение упорядоченных ключей в дереве и зависимость стоимости
операций от его формы.

Реализовать обобщённое бинарное дерево поиска без автоматической балансировки.
Профиль API — коллекция упорядоченных ключей с поиском, добавлением и удалением
по ключу. Организация хранения — связанные узлы дерева; заранее заданного
ограничения количества элементов нет. Коллекции BCL как хранилище запрещены.

Предоставить:

- поиск ключа, добавление и удаление по ключу;
- количество элементов, проверку пустоты, высоту и очистку дерева;
- симметричный, прямой и обратный обходы без удаления элементов.

Самостоятельно выбрать способ сравнения ключей, политику равных ключей,
публичный API и соглашение об измерении высоты. Выбор элемента в основных
операциях определяется ключом и отношением порядка; индексный доступ
и последовательный поиск по условию в эту задачу не входят.

Поиск, добавление и удаление должны занимать O(h), где h — высота дерева;
полный обход и очистка — O(n), получение количества и проверка пустоты — O(1).
Для высоты указать стоимость выбранного решения. По сравнению с последовательным
поиском в списке дерево позволяет использовать порядок ключей для поиска:
при высоте O(log n) основные операции имеют стоимость O(log n), но без
балансировки высота может достигать O(n).

АВЛ, обход по уровням, соседние ключи, диапазонные запросы и порядковые
статистики остаются направлениями дальнейшего углубления и не входят
в текущую задачу. Для каждой операции, допускающей итеративный и рекурсивный
алгоритмы, обязательны обе реализации по
[универсальному правилу](specification.md#открытое-изучение-тем-и-выбор-следующей-задачи).
Их можно реализовывать и проходить ревью по отдельности; готовность одного
варианта не означает завершения обоих.

Лабораторный полигон автора:
`tests/Practice.DataStructures.Tests/Trees/BinarySearchTree/BinarySearchTreeLaboratoryTests.cs`.
Он запускается до появления реализации Core. Содержимым до завершения обоих
этапов ревью управляет автор. Затем выполняется итоговое оформление по
[порядку работы](testing.md#порядок-работы-над-задачей).

Текущее решение автора хранит пары ключ–значение и запрещает равные по
comparer ключи. Реализованная часть и состояние промежуточного ревью —
в [плане](study-plan.md#текущее-состояние-и-точки-продолжения).
Перечень операций выше остаётся целью задачи, а не описанием готового API.
