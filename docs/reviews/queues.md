# Ревью очередей

Реализации: `ArrayQueue<T>` и `LinkedQueue<T>`.
Оба этапа ревью завершены. Функциональных ошибок и оставшихся замечаний
по архитектуре, коду и публичному API не обнаружено.

По явному поручению автора заполнены части `TODO Codex`: исключения пустых
`Dequeue` и `Peek`, обобщённый и необобщённый перебор и вложенные перечислители.
По последующему запросу автора добавлено собственное версионирование очередей.
Laboratory-полигон сохранён.

Обе очереди добавляют в конец и извлекают из начала собственного списка.
`Peek` сохраняет состояние, `Count` и `IsEmpty` соответствуют хранилищу.
Пустые `Dequeue` и `Peek` выбрасывают `InvalidOperationException` без изменения
состояния. Очередь на массиве сохраняет амортизированное O(1) для добавления
и O(1) для извлечения; связная очередь выполняет эти операции за O(1).
Очистка и последующее использование корректны.

Временный диагностический прогон вне решения сравнил каждую реализацию
с `System.Collections.Generic.Queue<T>` для seed 0, 12345 и 71817:
по 12 000 смешанных операций на каждый seed, отдельно для `int` и `object?`.
Всего выполнено 144 000 операций. После каждого шага проверялись количество,
пустота, чтение головы и порядок обоих вариантов перебора. Входные значения
включали дубликаты, null, повторные ссылки и крайние значения int.
Сравнение объектов проверяло сохранение ссылочной идентичности.

Отдельно проверены независимые обходы, Current до начала и после конца,
повторный MoveNext после конца, неподдерживаемый Reset, инвалидирование
при Enqueue, Dequeue и Clear до начала, во время и после конца обхода,
а также после Dispose. Clear инвалидирует обход даже пустой очереди;
отклонённые операции его сохраняют. Проверены полное опустошение и повторное
использование. Диагностический прогон не добавляет контрактные тесты в Tests.

Каждая очередь хранит собственную версию. Успешные Enqueue и Dequeue и каждый
Clear, включая очистку пустой очереди, увеличивают её через unchecked.
Peek и отклонённый Dequeue версию не меняют. Перечислитель запоминает версию
при создании и проверяет её в MoveNext и обоих вариантах Current до проверки
состояния. Обход элементов делегируется внутреннему списку без копирования.
Dispose завершает обход обеих очередей; повторный Dispose безопасен.
При неизменной очереди MoveNext после Dispose возвращает false, Current
выбрасывает InvalidOperationException. Изменения после Dispose обнаруживаются
собственной проверкой версии, даже когда внутренний обход больше не вызывается.

После изменения повторный временный прогон проверил все три изменяющие
операции и пару Dequeue/Enqueue с сохранением Count до начала, во время,
после завершения и после Dispose. Проверены чтение без инвалидирования,
отклонённые операции, очистка пустой очереди, повторный Dispose и оба Current.
Дополнительно выполнено по 12 000 смешанных операций с эталонной Queue<int>
для каждой реализации, seed 12345. Все проверки прошли.

## Архитектура, код и публичный API

Имена ArrayQueue и LinkedQueue и имена файлов соответствуют словарю:
FIFO-очередь на массиве и на связанных узлах соответственно. Обе реализации
имеют одинаковый базовый API: Count, IsEmpty, Enqueue, Dequeue, Peek, Clear
и IEnumerable<T>. Индексаторы, курсоры и полный API списков скрыты композицией.
Коллекций BCL как хранилища нет. Дополнительный интерфейс, поиск и публичное
управление вместимостью для текущей задачи не требуются.

Перечислители используют готовый обход списков, собственную версию очереди
и признак Dispose. Дублирование небольших частных обёрток не требует общей
инфраструктуры. Семантика обоих вариантов обхода согласована.

LinkedQueue.Peek использует Values.TryFirst без создания курсора.
Dequeue проверяет отрицательный результат TryRemoveAfter и возвращает item
без подавления nullable-диагностики. Версия увеличивается только после
успешного удаления. После исправлений временный диагностический прогон
подтвердил исключения пустых операций без инвалидирования, успешное удаление
с инвалидированием обычного и освобождённого перечислителей, null,
ссылочную идентичность, чтение без изменения состояния и повторное использование.

XML-комментарии оформлены и сверены со словарём, именами, публичным API
и фактическим поведением. Указаны FIFO, организация хранения, политика
вместимости, стоимость операций, ошибки и полный контракт перечисления.

Общие контрактные тесты находятся в Collections/Queue/QueueContractTests.cs.
ArrayQueueTests и LinkedQueueTests создают адаптеры с прямым отображением
публичных операций, без изменений объявлений Core ради тестов. 82 проверки
охватывают обе реализации, включая рост, циклы чередования операций,
сравнение с эталонной очередью, null, ссылки, ошибки и состояния перечислителей.
Проверки хранения собственных списков остаются в их существующих тестах.

Единственный Laboratory-факт заменён демонстрацией обеих очередей на одном
случайном входе: заполнение, частичное извлечение, последующее заполнение,
FIFO-обход и извлечение, ошибки, инвалидирование, Dispose, очистка и повторное
использование. Seed и параметры выводятся; поддерживается DATASTRUCTURES_LAB_SEED.

## Проверки

Locked restore, сборка Release без предупреждений, проверка форматирования
и все 532 обычных теста прошли, включая 82 проверки очередей. Демонстрация
прошла с новым случайным seed и с seed 12345; неверный seed отклоняется
с понятной ошибкой.
Rider inspections выполнены для всех изменённых C#-файлов. Оставлены подсказки
об ожидаемых аллокациях хранилищ, перечислителей, адаптеров, массивов и делегатов,
boxing и приведении к IEnumerable для проверки необобщённого обхода.
Явные Dispose внутри using проверяют завершение обхода и повторяемость Dispose;
using гарантирует освобождение при падении Assert. Делегаты Assert не сохраняются
за пределами проверок. Функциональных проблем эти замечания не указывают.
