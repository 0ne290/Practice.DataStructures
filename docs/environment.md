# Окружение разработчика

Пользователь самостоятельно устанавливает и обновляет SDK, IDE, Git и оболочку.
Репозиторий не закрепляет номера версий этих инструментов. Нейросеть использует
фактически доступное окружение и сохраняет проверенные сведения в
`environment.local.json` в корне репозитория. Этот файл исключён из Git.

## Настройки проекта

- `global.json` содержит только `allowPrerelease: false`: выбирается самый новый
  стабильный SDK, доступный вызываемому `dotnet`. Номера версии и ограничения
  feature band нет. Это поведение описано в [документации .NET](https://learn.microsoft.com/en-us/dotnet/core/tools/global-json).
- `TargetFramework` в `Directory.Build.props` задаёт целевую платформу библиотеки
  и тестов. Для сборки нужен SDK, поддерживающий эту платформу; для запуска
  тестов — соответствующий runtime. Обновление инструментов не меняет
  целевую платформу автоматически.
- `LangVersion` явно не задаётся. SDK выбирает C# по целевой платформе, как
  описано в [документации C#](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-versioning).
- NuGet-пакеты входят в зависимости проекта. Их версии находятся в `.csproj`
  и `packages.lock.json`; обновляются через менеджер пакетов с последующими
  проверками из README. Раздел `libraries` локального кэша содержит производную
  сводку зависимостей для выбора API.

## Работа нейросети с кэшем

1. Перед действием, зависящим от окружения или сторонних библиотек, прочитать
   `environment.local.json`.
   Проверять только компоненты, нужные для текущей задачи.
2. Если файла нет, исследовать нужные компоненты и создать файл. Если отсутствует
   раздел или нужное поле, получить только недостающие сведения. Сохранять
   остальные разделы и поля, включая пользовательские дополнения.
3. Для уже известных сведений использовать кэш без повторного опроса инструментов.
   Дата записи сама по себе не требует обновления. Отсутствие записи означает
   отсутствие сведений, а не отсутствие установленного компонента.
4. Обновить затронутые сведения, если пользователь сообщил об обновлении,
   сохранённый путь перестал существовать или вывод команды противоречит кэшу.
   При ошибке SDK/runtime сначала перепроверить раздел `dotnet`. После изменения
   целевой платформы пересчитать зависящие от неё сведения о C# и runtime.
5. Записывать фактическую версию, путь к инструменту, источник сведений и время
   проверки в UTC. Если компонент недоступен, записать `available: false`, источник
   и время проверки; не придумывать версию и не устанавливать инструмент
   ради заполнения кэша.

Кэш — обычный JSON-объект с отдельными разделами компонентов. Имена разделов:

| Раздел | Сведения |
| --- | --- |
| `dotnet` | Путь к CLI, выбранный SDK, MSBuild, доступные runtimes; целевая платформа и выбранная версия C# при работе с кодом |
| `git` | Путь и версия Git |
| `shell` | Путь, название и версия оболочки, используемой для команд |
| `ide` | Название, версия, build и путь IDE, если задача зависит от IDE |
| `libraries` | Сводки зависимостей по проектам, версии пакетов и хеши файлов-источников |

В каждом заполненном разделе инструмента используются `executable`, `version`, `source`
и `checkedAtUtc`. Дополнительные поля добавляются по текущей необходимости.
`dotnet.version` — выбранная версия SDK. Если обнаружены другие установки,
их можно сохранить в `dotnet.otherInstallations`, отдельно от выбранной.
Удаление отдельного поля требует повторного получения этого сведения;
если команда возвращает также связанные поля, их можно обновить вместе.

Сначала исследовать `dotnet` из PATH. При нескольких установках различать
используемый CLI, остальные установки и настройки IDE: у них могут быть разные
SDK и runtimes. Для команд использовать сохранённый `executable`; примеры
`dotnet ...` в README подразумевают этот путь. Если инструмент из PATH подходит,
использовать его. При необходимости другого CLI проверить его и записать выбор
в кэш, не меняя системный PATH или настройки IDE автоматически.

При восстановлении NuGet учитывать контекст запуска. Сохранить доступный IDE
каталог пакетов в `dotnet.nugetPackagesPath` и контекст восстановления в
`dotnet.restoreContext`. Изолированная среда агента может записать в общие `obj`
пути к своему закрытому кэшу: тогда проверки агента проходят, а IDE не разрешает
ссылки. Для открытого в IDE решения выполнять restore и проверки из README
через терминал IDE или другой проверенный пользовательский контекст. После
restore сверять `packageFolders` в `obj/project.assets.json` с доступным IDE
каталогом. После исправления ссылок проверять также диагностику файла в IDE.

## Библиотеки и выбор API

В `libraries` хранить сводки по имени проекта. Каждая сводка содержит:

- `targetFramework` — платформу, для которой прочитаны зависимости;
- `packages` — записи по NuGet ID: `requested` из проекта, фактически разрешённую
  `version` из lock-файла и `type` (`Direct` или `Transitive`);
- `sourceFiles` — относительные пути файлов-источников и их SHA-256;
- `checkedAtUtc` — время проверки в UTC.

Записывать прямые зависимости проекта. Транзитивные добавлять, когда их API или
поведение нужны для текущей задачи. Семейство API, вариант пакета, способ запуска
и ссылки на официальную документацию сохранять, когда они важны для выбора
подхода. Номер пакета не всегда совпадает с названием семейства API: пакеты
`xunit.v3.*` относятся к xUnit.net v3, в том числе при версии пакета `4.x`.
Вариант `mtp-off` отключает MTP; выбор вариантов описан в
[документации xUnit](https://xunit.net/docs/getting-started/v3/microsoft-testing-platform).

Перед использованием сводки сравнивать хеши её `sourceFiles` с текущими файлами.
Для текущего тестового проекта источники — `.csproj`, `packages.lock.json` и
`Directory.Build.props`. Если хеши совпадают и нужная запись заполнена,
использовать кэш. Если файл изменился, перечитать сведения затронутого проекта;
если отсутствует отдельный пакет или поле, дополнить только недостающие сведения.
Остальные разделы сохранять. Проверка хешей не требует опроса установленных
инструментов или сети. Хеши служат для проверки актуальности кэша.

При расхождении проекта и lock-файла сначала выполнить restore в пользовательском
контексте, затем повторно прочитать зависимости. При ошибке locked restore
устранить рассогласование; не выдавать прежнюю сводку за актуальную.
`obj/project.assets.json` можно использовать для проверки реально восстановленных
зависимостей; этот генерируемый файл зависит от устройства и контекста запуска.
Значения `requested` и разрешённая версия могут различаться, как описано в
[документации NuGet](https://learn.microsoft.com/en-us/nuget/consume-packages/package-references-in-project-files).

Для нового кода выбирать рекомендуемые подходы и API, доступные в подключённой
версии библиотеки. Перед использованием незнакомого API сверяться с официальной
документацией для этой версии, а при необходимости — с XML-документацией и
сигнатурами восстановленного пакета. Учитывать рекомендации анализаторов и
пометки `Obsolete`; устаревший API использовать только с конкретным обоснованием.
Давно существующий поддерживаемый API сам по себе не считается legacy. Соглашения
о читаемости тестов действуют согласно `tests/CODE_CONVENTIONS.md`.

Версия из кэша означает подключённую версию, а не последнюю опубликованную.
Проверять наличие новых выпусков при задаче обновления библиотек. Само заполнение
кэша не меняет зависимости проекта. После обновления пакетов обновить lock-файл
и соответствующую сводку `libraries`.

## Получение сведений

Запускать из корня репозитория только команды для недостающих сведений:

```powershell
# Расположение инструментов.
Get-Command dotnet, git | Select-Object Name, Source

# SDK и runtimes выбранного dotnet.
dotnet --version
dotnet --list-runtimes

# Фактические параметры сборки проекта и версия C#.
dotnet msbuild src/Practice.DataStructures.Core/Practice.DataStructures.Core.csproj -getProperty:NETCoreSdkVersion,MSBuildVersion,TargetFramework,LangVersion

# Git и текущая PowerShell.
git --version
$PSVersionTable.PSVersion.ToString()
(Get-Process -Id $PID).Path
```

Версию IDE получать из её сведений о продукте или `product-info.json`
в каталоге фактически используемой установки. Команды — источники сведений,
а не обязательный полный опрос перед каждой задачей.

## Сброс после обновления

- Удалить `environment.local.json`, чтобы исследовать окружение заново.
- Удалить один раздел, например `dotnet`, чтобы обновить только этот компонент.
- Удалить сводку проекта или запись пакета в `libraries`, чтобы перечитать
  соответствующие зависимости.
- Удалить отдельное поле, чтобы получить только недостающие сведения.

При редактировании сохранять корректный JSON. На новом устройстве после
клонирования кэша нет; нейросеть создаёт его по мере необходимости.
