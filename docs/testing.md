# Тестовая лаборатория

Tests содержит проверки публичного API Core, эталоны .NET, фикстуры,
воспроизводимые данные и измерительные сценарии. API учебных структур пока не
определён; предметные тесты добавляются после согласования контрактов.

Соглашения о стиле, видимости, организации и review тестового кода находятся
в [tests/CODE_CONVENTIONS.md](../tests/CODE_CONVENTIONS.md).

## Обычные проверки

Используйте xUnit v3: `[Fact]` для одного сценария, `[Theory]` для наборов данных.
Явно разделяйте Arrange / Act / Assert, называйте тесты по действию и ожидаемому
результату. Проверяйте нормальные случаи, границы, ошибки, инварианты и
детерминированность. `ITestOutputHelper` дополняет Assert, но не заменяет его.
Коллекции BCL допустимы в качестве эталона в Tests.

Обычный прогон:

```powershell
dotnet test Practice.DataStructures.sln --settings .runsettings
```

`.runsettings` исключает обе лабораторные категории. Он автоматически подключён
через `RunSettingsFilePath` в Tests. Отсутствие обнаруженных тестов считается
ошибкой, чтобы поломка настройки runner не выглядела успешным прогоном.

## Лабораторные сценарии и измерения

Помечайте диагностику `[Trait("Category", "Laboratory")]`, измерения —
`[Trait("Category", "Performance")]`. Для их запуска явно выберите
`laboratory.runsettings` без исключающего фильтра и укажите нужную категорию:

```powershell
dotnet test Practice.DataStructures.sln --configuration Release --settings laboratory.runsettings --filter "Category=Laboratory" --logger "console;verbosity=detailed"
dotnet test Practice.DataStructures.sln --configuration Release --settings laboratory.runsettings --filter "Category=Performance" --logger "console;verbosity=detailed"
```

Эти команды предназначены для будущих сценариев. В первом каркасе таких тестов
ещё нет, поэтому запуск категории сейчас завершится ошибкой отсутствия тестов.

Лабораторный сценарий вызывает публичный API Core и проверяет результат.
Используйте фиксированный seed, сохраняйте seed и параметры во входных данных
или выводе. Нужные тесту данные держите рядом с его проверками; файловые данные
явно копируйте в output через csproj и загружайте относительно `AppContext.BaseDirectory`.
Не привязывайте сценарии к текущей рабочей папке или абсолютным локальным путям.

Для измерений: Release, запуск без отладчика, прогрев, повторные прогоны,
эквивалентные входы и проверка корректности до замера. Генерация данных и вывод
диагностик должны находиться вне измеряемого участка. Записывайте время,
аллокации, размер входа, seed и окружение. Не используйте абсолютные пороги
времени как критерий корректности. Измерения запускайте отдельно от обычных
тестов и отключайте параллельность для коллекции с измерительными сценариями.

## IDE

Откройте `Practice.DataStructures.sln` в Rider и используйте встроенный xUnit
runner. Для общего прогона настройте поддержку `.runsettings` и выберите файл
из корня решения; для лабораторной сессии выберите `laboratory.runsettings`
и нужную категорию. Применение VSTest-настроек зависит от runner IDE.
Если настройки фильтра IDE не применяются, исключите категории Laboratory и
Performance в обычной тестовой сессии и запускайте их отдельными сессиями.
CLI-команды выше задают единый воспроизводимый способ локального запуска.

Tests использует автоматически создаваемую точку входа xUnit v3.
Не добавляйте собственный `Program.cs` или учебное консольное меню.
