# Тестовая лаборатория

Tests содержит проверки публичного API Core, эталоны .NET, фикстуры,
воспроизводимые данные и измерительные сценарии. В `Collections/DynamicArray/DynamicArrayTests.cs`
проверяются создание динамического массива, добавление, рост, доступ по индексу
и ошибки аргументов. Тесты остальных структур добавляются после двух этапов ревью.
В `Collections/DynamicArray/DynamicArrayRemovalTests.cs` проверяются удаление по индексу,
сохранение порядка и вместимости, ошибки и повторное использование массива.
В `Collections/DynamicArray/DynamicArrayStorageTests.cs` отдельно проверяется очистка
освободившейся ячейки для значений, ссылок и структур со ссылочными полями.
Эти проверки внутреннего инварианта обращаются к хранилищу через reflection.
В `Collections/DynamicArray/DynamicArrayEnumerationTests.cs` проверяются порядок перебора,
пустая последовательность, повторные и вложенные обходы, ранний выход и оба
варианта `IEnumerable`. В `Collections/DynamicArray/DynamicArrayInvalidationTests.cs` проверяется
обнаружение изменений: успешные `Add`, `RemoveAt` и запись через индексатор
инвалидируют старые перечислители, а чтение, отклонённая запись и удаление
по недопустимому индексу сохраняют их работоспособность.
В `Collections/DynamicArray/DynamicArrayClearTests.cs` проверяются очистка, сохранение
вместимости, повторное использование и инвалидирование перечислителей даже при
очистке пустого массива. Проверки очистки ячеек находятся отдельно в
`DynamicArrayStorageTests.cs`. В `Collections/DynamicArray/DynamicArraySearchTests.cs`
проверяются `IndexOf` и `Contains` с `IndexedPredicate<T>`: первое совпадение,
порядок вызовов и остановка поиска, выбор по позиции, ссылке и полям, значения
по умолчанию и `null` среди элементов, вложенный поиск, исключения условия,
обнаружение изменений из условия и сохранение состояния при чтении.
Предикат обязан быть ненулевым; проверка этого предусловия намеренно отсутствует,
тесты не требуют определённого поведения при передаче `null` вместо делегата.
Полный контракт обхода описан у `DynamicArray<T>.GetEnumerator()` в Core.

Соглашения о стиле, видимости, организации и review тестового кода находятся
в [tests/CODE_CONVENTIONS.md](../tests/CODE_CONVENTIONS.md).

## Порядок работы над задачей

1. Нейросеть ставит задачу в академическом стиле: описывает структуру, необходимые
   операции, доступные сведения и способ выбора элементов — по индексу или по
   условию. Отталкиваться от традиционного назначения структуры: явно обозначать
   характерные возможности, их стоимость и преимущества перед уже изученными
   структурами. Постановка не является полной спецификацией-ТЗ. Не выдавать заранее
   сигнатуры, устройство решения, инварианты, перечни граничных случаев и правила
   отдельных веток без запроса автора. Автор открывает их во время написания кода.
2. Сразу создавать одну точку запуска Laboratory как полигон автора, без
   обязательного полного сценария и без заранее подготовленных контрактных тестов.
   Полигон должен запускаться, даже если Core ещё не содержит объявлений задачи;
   не создавать ради него объявления или заглушки Core без явного запроса.
3. Автор самостоятельно выбирает API и реализует Core. До окончания ревью
   он использует лабораторный полигон для собственных запусков и отладки.
4. Первое ревью проверяет только функциональную корректность и надёжность.
   На этом этапе исследовать инварианты, граничные случаи, ошибки, состояния
   и ветки выполнения. Сообщать обнаруженные проблемы, автор исправляет их.
   Повторять проверку до устранения найденных функциональных проблем.
   Архитектуру, стиль, чистоту кода и API на этом этапе не оценивать.
5. После завершения функционального ревью отдельно оценивать архитектуру,
   чистоту кода и API. Автор вносит исправления, нейросеть повторяет ревью.
   Если изменения затронули поведение, снова проверить его корректность.
6. После завершения обоих этапов нейросеть оформляет спецификацию по принятому
   решению: XML-комментарии, обычные тесты и полноценный лабораторный сценарий.
   В существующей точке запуска заменить авторские эксперименты демонстрацией
   итогового решения, а не создавать второй демонстрационный Fact.
   XML-комментарии разрешено добавлять в Core; реализацию, объявления и сигнатуры
   без отдельного явного запроса не менять.

Не дорабатывать полигон автора и не заменять его эксперименты до финального
оформления без отдельного запроса. Требования к полной демонстрации ниже относятся
к итоговому сценарию; учебный полигон не обязан заранее им соответствовать.
При расширении существующей задачи повторять тот же порядок, использовать её
имеющуюся лабораторную точку запуска и сохранять проверки готовых возможностей.
Если старые тесты расходятся с изменённым решением, сначала отличить намеренное
изменение от ошибки. Не ослаблять проверки ради зелёного прогона. Если намерение
неясно, уточнить его у автора. Итоговые тесты и документы синхронизировать с
принятыми решениями; актуальные намеренные решения автора имеют приоритет над
исходной спецификацией.

## Завершённое упражнение: стек на связном хранении

Реализовать `LinkedStack<T>` — обобщённый стек LIFO на связном хранении.
Предоставить добавление на вершину, извлечение с вершины, чтение вершины
без удаления, количество элементов, проверку пустоты, очистку и последовательный
перебор через `foreach` от вершины к основанию без удаления элементов.

Добавление, извлечение и чтение вершины должны занимать O(1), получение
количества элементов и проверка пустоты — O(1), полный перебор — O(n).
В отличие от стека на массиве, рост связного стека не требует переноса
всех накопленных элементов в более вместительное хранилище.

Обе реализации стека должны предоставлять совместимый публичный контракт,
чтобы после ревью к ним можно было применить общие контрактные тесты.
Ориентир — принятые операции `ArrayStack<T>`; детали реализации и оформление
API остаются за автором. Использовать собственные связные структуры;
ранее написанные примитивы можно переиспользовать, если сохраняется требуемая
сложность. Коллекции BCL в качестве хранилища запрещены.

Оба этапа ревью завершены. По явному запросу автора устранены лишние курсоры
в операциях вершины, а перечислитель переиспользует обход списка через закрытую
обёртку. Обёртка сохраняет контракт стека после Dispose и обнаружение изменений.
Clear выполняется за O(1); старый перечислитель может удерживать прежние узлы.
XML-комментарии оформлены. Результаты: [LinkedStack](reviews/linked-stack.md).

Общие проверки операций и перечисления находятся в `Collections/Stack/StackContractTests.cs`.
Классы `ArrayStackTests` и `LinkedStackTests` подключают к ним соответствующую
реализацию через тестовый адаптер без изменения публичного API Core.
Один набор проверяет обе реализации: LIFO, ошибки, очистку, null, идентичность,
смешанные операции с фиксированным seed, оба интерфейса перечисления и состояния
перечислителя, включая изменения после Dispose.

Единственный Laboratory-факт в `Collections/Stack/StackLaboratoryTests.cs`
демонстрирует оба стека на одних случайных входных данных. Seed и параметры
печатаются до операций; повтор поддерживается через `DATASTRUCTURES_LAB_SEED`.
Запуск — той же командой, что приведена в разделе стека на массиве.

## Завершённое упражнение: стек на массиве

Реализовать `ArrayStack<T>` — обобщённый стек с порядком LIFO:
последний добавленный элемент извлекается первым. Предоставить добавление
на вершину, извлечение с вершины, чтение вершины без удаления, количество
элементов, проверку пустоты и очистку.

В отличие от списка, стек ограничивает доступ вершиной. Чтение вершины
и извлечение должны занимать O(1), добавление — амортизированное O(1).
Использовать собственное хранилище на массиве; ранее написанный
`DynamicArray<T>` можно переиспользовать. API и поведение операций выбирает автор.

Реализация на массиве завершена. Оба этапа ревью пройдены; по TODO автора
для пустого стека выбрано `InvalidOperationException` в `Pop` и `Peek`.
XML-комментарии и обычные тесты оформлены. Проверяются LIFO, рост хранилища,
чтение без удаления, ошибки, очистка и повторное использование, null,
дубликаты, ссылочная идентичность и смешанные операции с эталонным стеком.
Результаты ревью: [ArrayStack](reviews/array-stack.md).

По запросу автора добавлен `IEnumerable<T>`: `foreach` проходит от вершины
к основанию, не удаляя элементы. Перечислители независимы; Push, успешный Pop
и каждый Clear инвалидируют их. Полный контракт описан у GetEnumerator.
Проверки обхода включены в общие `Collections/Stack/StackContractTests.cs`.

`Collections/Stack/StackLaboratoryTests.cs` показывает заполнение случайными
данными, foreach и обнаружение изменений во время обхода,
извлечение в обратном порядке, ошибки пустого стека, очистку и
повторное использование; поддерживает `DATASTRUCTURES_LAB_SEED`.
Запуск: `dotnet test Practice.DataStructures.sln --configuration Release --settings laboratory.runsettings --filter "FullyQualifiedName~StackLaboratoryTests" --logger "console;verbosity=detailed"`.
Связная реализация включена в этот же сценарий. Вычисление выражений в обратной
польской нотации остаётся отдельным упражнением.

## Завершённое упражнение: двусвязный список

Традиционные преимущества перед односвязным списком: удаление хвоста за O(1),
прямой и обратный проход, поиск последнего совпадения с конца, локальные вставки
и удаление известного элемента за O(1), выбор позиции с ближайшего конца.
Поиск произвольного значения остаётся O(n).

По явному запросу автора реализация, API, проверки и демонстрация выполнены
нейросетью целиком. Результаты самопроверки корректности и отдельного разбора
архитектуры: [DoublyLinkedList](reviews/doubly-linked-list.md).

Публичный API скрывает узлы и связи. `First`, `Last`, `FindFirst`, `FindLast`
и `GetCursorAt` предоставляют независимый курсор. Курсор читает и заменяет
значение, движется в обе стороны и выполняет вставки рядом и удаление за O(1).
Неудачное движение оставляет курсор на текущем элементе. Изменения других
элементов сохраняют курсор; удаление его элемента и очистка инвалидируют его.
Числового индекса у курсора нет: вставка перед ним меняет индекс, но не элемент.

`FindFirst` проверяет от головы, `FindLast` — от хвоста; условие всегда получает
позицию от головы. `GetCursorAt` проходит O(min(index, Count − 1 − index)) узлов.
Операции с концами и очистка выполняются за O(1). Прямой перебор и `Reverse()`
проходят по связям без копии, обнаруживая изменения списка. Старые курсоры после
очистки могут удерживать старую цепочку в памяти до освобождения ссылок на них.

В `Collections/DoublyLinkedList/` находятся проверки публичного поведения,
курсоров, поиска и перечисления. Проверка взаимности связей и отсоединения
удалённых узлов отделена от контрактных проверок. Обычные сценарии детерминированы.

Единственный Laboratory-сценарий —
`Collections/DoublyLinkedList/DoublyLinkedListLaboratoryTests.cs`. Показывает поиск
с обоих концов, локальное редактирование курсором, обратный обход, устойчивость
курсоров и ожидаемые ошибки. Seed и параметры выводятся до операций Core.

```powershell
dotnet test Practice.DataStructures.sln --settings laboratory.runsettings --filter "FullyQualifiedName~DoublyLinkedListLaboratoryTests" --logger "console;verbosity=detailed"
```

Для повтора добавить `--environment DATASTRUCTURES_LAB_SEED=12345`, заменив
число на seed из вывода. Неверное значение переменной вызывает понятную ошибку.

## Завершённое упражнение: односвязный список

Реализовать обобщённый односвязный список `SinglyLinkedList<T>` на собственных
узлах, скрытых от пользователя коллекции. Список должен поддерживать добавление
в начало и конец, чтение, изменение и удаление элемента по условию, поиск позиции
и проверку наличия по условию, очистку и последовательный перебор. Предоставить
количество элементов. Условию доступны элемент и его текущая позиция в списке.
Конкретный API и поведение операций автор выбирает самостоятельно.

Если по отдельному решению автора одной структуре требуется несколько явно
разделённых API, предоставлять их через отдельные объекты доступа к общему
хранилищу, получаемые через свойства коллекции. Каждый объект открывает только
операции своего API; одного специального именования методов на самой коллекции
для такого разделения недостаточно. Это способ организации нескольких API,
а не требование создавать несколько API у каждой структуры.

По запросу автора этот способ применён к односвязному списку: `list.Values`
предоставляет прежние операции с прежними именами и контрактами; `list.Cursors`
создаёт курсоры. На самой коллекции остаются общие `Count` и `IEnumerable<T>`.
Прямых публичных копий методов Values нет. Остальные структуры на этот способ
разделения API не переводятся без отдельного решения автора.

Код расположен в `src/Practice.DataStructures.Core/Collections/SinglyLinkedList/`:
`SinglyLinkedList.cs` содержит состояние и общие механизмы, `ValueApi.cs` — операции
над значениями, `CursorApi.cs` — получение курсоров, `Cursor.cs` — курсор,
`Node.cs` — узел, `Enumerator.cs` — перечислитель. Каждый файл содержит один
компонент; partial-объявления сохраняют вложенность типов. Методы API реализованы
в своих компонентах без приватных копий на самом списке. Изменения цепочки
в обоих API используют общие механизмы вставки, удаления и замены значения.

Курсор поддерживает `Value`, `MoveNext`, `InsertAfter` и `TryRemoveAfter`.
Все эти действия выполняются за O(1). `BeforeFirst` обозначает позицию перед
головой, включая пустой список, и позволяет вставлять и удалять голову теми же
операциями «после позиции». В этой позиции чтение и запись Value недоступны.
`First`, `Last` возвращают курсоры на концы либо null; `FindFirst` ищет по условию
за O(n), передавая элемент и его позицию от нуля. Предшественник не сохраняется;
движения назад, вставки перед и удаления текущего элемента у курсора нет.

Курсоры независимы и остаются на выбранных элементах при изменениях через любой
из двух API. Удаление выбранного элемента инвалидирует курсор; очистка
инвалидирует все курсоры, включая BeforeFirst. Неудачное движение вперёд
сохраняет позицию. Мутации через оба API обнаруживаются поиском и перечислителями.
Старые курсоры после очистки могут удерживать старую цепочку до освобождения ссылок.

```csharp
var list = new SinglyLinkedList<int>();
list.Values.AddLast(10);
var cursor = list.Cursors.BeforeFirst;
cursor.InsertAfter(5); // Новая голова: [5, 10].
cursor.MoveNext();     // Курсор на 5.
cursor.InsertAfter(7); // [5, 7, 10], без повторного поиска.
list.Values.Contains((value, _) => value == 7); // Оба API видят одну цепочку.
```

Оба этапа ревью завершены. В `Collections/SinglyLinkedList/` находятся обычные
проверки операций и состояния, поиска, перечисления и обновления ссылочных объектов.
Проверяются отсутствие и хранимые null/default, первое совпадение, позиции,
ошибки делегатов, обнаружение изменений и сравнение с BCL на 500 операциях
с фиксированным seed. Общий базовый класс коллекций и перечислителей не вводится.

Демонстрация: `Collections/SinglyLinkedList/SinglyLinkedListLaboratoryTests.cs`.
Показывает вставки, поиск, замену, удаление, обновление ссылочного объекта,
инвалидирование обхода, ожидаемые ошибки, очистку и повторное использование.
Запуск со случайным seed:

```powershell
dotnet test Practice.DataStructures.sln --settings laboratory.runsettings --filter "FullyQualifiedName~SinglyLinkedListLaboratoryTests" --logger "console;verbosity=detailed"
```

Для повтора добавить `--environment DATASTRUCTURES_LAB_SEED=12345`, заменив
число на seed из вывода. Неверное значение переменной вызывает понятную ошибку.

## Обычные проверки

Используйте xUnit v3: `[Fact]` для одного сценария, `[Theory]` для наборов данных.
Явно разделяйте Arrange / Act / Assert, называйте тесты по действию и ожидаемому
результату. Проверяйте нормальные случаи, границы, ошибки, инварианты и
детерминированность. `ITestOutputHelper` дополняет Assert, но не заменяет его.
Коллекции BCL допустимы в качестве эталона в Tests.

Обычный прогон:

```powershell
dotnet test Practice.DataStructures.sln --settings .runsettings
```

`.runsettings` исключает обе лабораторные категории. Он автоматически подключён
через `RunSettingsFilePath` в Tests. Отсутствие обнаруженных тестов считается
ошибкой, чтобы поломка настройки runner не выглядела успешным прогоном.

## Единая лабораторная точка запуска

На каждую задачу практикума должна быть ровно одна удобная точка запуска:
один `[Fact]` с `[Trait("Category", "Laboratory")]` в тематическом классе
`<Task>LaboratoryTests`. Сначала это полигон автора, после ревью — полноценная
демонстрация рядом с обычными тестами. Внутри этого метода могут быть
несколько последовательных этапов эксперимента. При нескольких реализациях
одной абстракции показывать их в том же сценарии. Отдельные обычные тесты и
измерения производительности в это ограничение не входят.

Итоговая демонстрация должна показывать основные возможности публичного API, интересные
изменения состояния и ожидаемые ошибки. Использовать случайные данные там, где
они делают эксперимент содержательнее. Вывод через `ITestOutputHelper` должен
позволять человеку понять, какие операции выполнены и что получилось.
Правильность результатов подтверждать через Assert.

По умолчанию при каждом запуске выбирать новый случайный seed. Выводить seed
и все параметры до операций Core, затем показывать входные данные, ход и итог
эксперимента. Случайные значения получать из одного локального `Random(seed)`.
Для точного повторения в том же окружении явно задавать seed через
`DATASTRUCTURES_LAB_SEED`; неверное значение должно давать понятную ошибку,
а не незаметно заменяться случайным seed. В обычных тестах сохранять
детерминированность, в сравнительных измерениях использовать фиксированные seed.

Текущая демонстрация: `Collections/DynamicArray/DynamicArrayLaboratoryTests.cs`. Она показывает
добавление случайных значений, рост вместимости, перебор через `foreach`, чтение
и замену через индексатор, удаление по случайным индексам, сохранение вместимости
после удаления всех элементов и повторное использование массива. Сценарий также
показывает обнаружение изменений во время обхода и ошибки аргументов,
поиск по значению и позиции среди дубликатов, обнаружение записи из условия,
очистку и повторное использование после очистки.
Новый случайный прогон и повтор конкретного прогона:

```powershell
dotnet test Practice.DataStructures.sln --configuration Release --settings laboratory.runsettings --filter "FullyQualifiedName~DynamicArrayLaboratoryTests" --logger "console;verbosity=detailed"

dotnet test Practice.DataStructures.sln --configuration Release --settings laboratory.runsettings --filter "FullyQualifiedName~DynamicArrayLaboratoryTests" --logger "console;verbosity=detailed" --environment DATASTRUCTURES_LAB_SEED=12345
```

В первой команде подразумевается, что `DATASTRUCTURES_LAB_SEED` не задана в
окружении. Во второй заменить `12345` на seed из нужного вывода. Параметр
`--environment` действует для запуска тестов и не сохраняет seed в следующих
сеансах. В IDE ту же переменную можно задать в окружении лабораторного запуска.

## Запуск лабораторных сценариев и измерений

Помечайте диагностику `[Trait("Category", "Laboratory")]`, измерения —
`[Trait("Category", "Performance")]`. Для их запуска явно выберите
`laboratory.runsettings` без исключающего фильтра и укажите нужную категорию:

```powershell
dotnet test Practice.DataStructures.sln --configuration Release --settings laboratory.runsettings --filter "Category=Laboratory" --logger "console;verbosity=detailed"
dotnet test Practice.DataStructures.sln --configuration Release --settings laboratory.runsettings --filter "Category=Performance" --logger "console;verbosity=detailed"
```

Демонстрация `DynamicArray<T>` уже доступна в категории Laboratory.
Сценариев Performance пока нет; их запуск завершится ошибкой отсутствия тестов.

Лабораторный сценарий вызывает публичный API Core и проверяет результат.
Сохраняйте seed и параметры во входных данных или выводе согласно правилам
демонстрации и измерений выше. Нужные тесту данные держите рядом с его проверками; файловые данные
явно копируйте в output через csproj и загружайте относительно `AppContext.BaseDirectory`.
Не привязывайте сценарии к текущей рабочей папке или абсолютным локальным путям.

Для измерений: Release, запуск без отладчика, прогрев, повторные прогоны,
эквивалентные входы и проверка корректности до замера. Генерация данных и вывод
диагностик должны находиться вне измеряемого участка. Записывайте время,
аллокации, размер входа, seed и окружение. Не используйте абсолютные пороги
времени как критерий корректности. Измерения запускайте отдельно от обычных
тестов и отключайте параллельность для коллекции с измерительными сценариями.

## IDE

Откройте `Practice.DataStructures.sln` в Rider и используйте встроенный xUnit
runner. Для общего прогона настройте поддержку `.runsettings` и выберите файл
из корня решения; для лабораторной сессии выберите `laboratory.runsettings`
и нужную категорию. Применение VSTest-настроек зависит от runner IDE.
Если настройки фильтра IDE не применяются, исключите категории Laboratory и
Performance в обычной тестовой сессии и запускайте их отдельными сессиями.
CLI-команды выше задают единый воспроизводимый способ локального запуска.

Tests использует автоматически создаваемую точку входа xUnit v3.
Не добавляйте собственный `Program.cs` или учебное консольное меню.
