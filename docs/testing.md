# Тестовая лаборатория

Tests содержит проверки публичного API Core, эталоны .NET, фикстуры,
воспроизводимые данные и измерительные сценарии. В `Collections/DynamicArrayTests.cs`
проверяются создание динамического массива, добавление, рост, доступ по индексу
и ошибки аргументов. Тесты остальных структур добавляются после двух этапов ревью.
В `Collections/DynamicArrayRemovalTests.cs` проверяются удаление по индексу,
сохранение порядка и вместимости, ошибки и повторное использование массива.
В `Collections/DynamicArrayStorageTests.cs` отдельно проверяется очистка
освободившейся ячейки для значений, ссылок и структур со ссылочными полями.
Эти проверки внутреннего инварианта обращаются к хранилищу через reflection.
В `Collections/DynamicArrayEnumerationTests.cs` проверяются порядок перебора,
пустая последовательность, повторные и вложенные обходы, ранний выход и оба
варианта `IEnumerable`. В `Collections/DynamicArrayInvalidationTests.cs` проверяется
обнаружение изменений: успешные `Add`, `RemoveAt` и запись через индексатор
инвалидируют старые перечислители, а чтение, отклонённая запись и удаление
по недопустимому индексу сохраняют их работоспособность.
В `Collections/DynamicArrayClearTests.cs` проверяются очистка, сохранение
вместимости, повторное использование и инвалидирование перечислителей даже при
очистке пустого массива. Проверки очистки ячеек находятся отдельно в
`DynamicArrayStorageTests.cs`. В `Collections/DynamicArraySearchTests.cs`
проверяются `IndexOf` и `Contains` с `IndexedPredicate<T>`: первое совпадение,
порядок вызовов и остановка поиска, выбор по позиции, ссылке и полям, значения
по умолчанию и `null` среди элементов, вложенный поиск, исключения условия,
обнаружение изменений из условия и сохранение состояния при чтении.
Предикат обязан быть ненулевым; проверка этого предусловия намеренно отсутствует,
тесты не требуют определённого поведения при передаче `null` вместо делегата.
Полный контракт обхода описан у `DynamicArray<T>.GetEnumerator()` в Core.

Соглашения о стиле, видимости, организации и review тестового кода находятся
в [tests/CODE_CONVENTIONS.md](../tests/CODE_CONVENTIONS.md).

## Порядок работы над задачей

1. Нейросеть ставит задачу в академическом стиле: описывает структуру, необходимые
   операции, доступные сведения и способ выбора элементов — по индексу или по
   условию. Постановка не является полной спецификацией-ТЗ. Не выдавать заранее
   сигнатуры, устройство решения, инварианты, перечни граничных случаев и правила
   отдельных веток без запроса автора. Автор открывает их во время написания кода.
2. Сразу создавать одну точку запуска Laboratory как полигон автора, без
   обязательного полного сценария и без заранее подготовленных контрактных тестов.
   Полигон должен запускаться, даже если Core ещё не содержит объявлений задачи;
   не создавать ради него объявления или заглушки Core без явного запроса.
3. Автор самостоятельно выбирает API и реализует Core. До окончания ревью
   он использует лабораторный полигон для собственных запусков и отладки.
4. Первое ревью проверяет только функциональную корректность и надёжность.
   На этом этапе исследовать инварианты, граничные случаи, ошибки, состояния
   и ветки выполнения. Сообщать обнаруженные проблемы, автор исправляет их.
   Повторять проверку до устранения найденных функциональных проблем.
   Архитектуру, стиль, чистоту кода и API на этом этапе не оценивать.
5. После завершения функционального ревью отдельно оценивать архитектуру,
   чистоту кода и API. Автор вносит исправления, нейросеть повторяет ревью.
   Если изменения затронули поведение, снова проверить его корректность.
6. После завершения обоих этапов нейросеть оформляет спецификацию по принятому
   решению: XML-комментарии, обычные тесты и полноценный лабораторный сценарий.
   В существующей точке запуска заменить авторские эксперименты демонстрацией
   итогового решения, а не создавать второй демонстрационный Fact.
   XML-комментарии разрешено добавлять в Core; реализацию, объявления и сигнатуры
   без отдельного явного запроса не менять.

Не дорабатывать полигон автора и не заменять его эксперименты до финального
оформления без отдельного запроса. Требования к полной демонстрации ниже относятся
к итоговому сценарию; учебный полигон не обязан заранее им соответствовать.
При расширении существующей задачи повторять тот же порядок, использовать её
имеющуюся лабораторную точку запуска и сохранять проверки готовых возможностей.
Если старые тесты расходятся с изменённым решением, сначала отличить намеренное
изменение от ошибки. Не ослаблять проверки ради зелёного прогона. Если намерение
неясно, уточнить его у автора. Итоговые тесты и документы синхронизировать с
принятыми решениями; актуальные намеренные решения автора имеют приоритет над
исходной спецификацией.

## Обычные проверки

Используйте xUnit v3: `[Fact]` для одного сценария, `[Theory]` для наборов данных.
Явно разделяйте Arrange / Act / Assert, называйте тесты по действию и ожидаемому
результату. Проверяйте нормальные случаи, границы, ошибки, инварианты и
детерминированность. `ITestOutputHelper` дополняет Assert, но не заменяет его.
Коллекции BCL допустимы в качестве эталона в Tests.

Обычный прогон:

```powershell
dotnet test Practice.DataStructures.sln --settings .runsettings
```

`.runsettings` исключает обе лабораторные категории. Он автоматически подключён
через `RunSettingsFilePath` в Tests. Отсутствие обнаруженных тестов считается
ошибкой, чтобы поломка настройки runner не выглядела успешным прогоном.

## Единая лабораторная точка запуска

На каждую задачу практикума должна быть ровно одна удобная точка запуска:
один `[Fact]` с `[Trait("Category", "Laboratory")]` в тематическом классе
`<Task>LaboratoryTests`. Сначала это полигон автора, после ревью — полноценная
демонстрация рядом с обычными тестами. Внутри этого метода могут быть
несколько последовательных этапов эксперимента. При нескольких реализациях
одной абстракции показывать их в том же сценарии. Отдельные обычные тесты и
измерения производительности в это ограничение не входят.

Итоговая демонстрация должна показывать основные возможности публичного API, интересные
изменения состояния и ожидаемые ошибки. Использовать случайные данные там, где
они делают эксперимент содержательнее. Вывод через `ITestOutputHelper` должен
позволять человеку понять, какие операции выполнены и что получилось.
Правильность результатов подтверждать через Assert.

По умолчанию при каждом запуске выбирать новый случайный seed. Выводить seed
и все параметры до операций Core, затем показывать входные данные, ход и итог
эксперимента. Случайные значения получать из одного локального `Random(seed)`.
Для точного повторения в том же окружении явно задавать seed через
`DATASTRUCTURES_LAB_SEED`; неверное значение должно давать понятную ошибку,
а не незаметно заменяться случайным seed. В обычных тестах сохранять
детерминированность, в сравнительных измерениях использовать фиксированные seed.

Текущая демонстрация: `Collections/DynamicArrayLaboratoryTests.cs`. Она показывает
добавление случайных значений, рост вместимости, перебор через `foreach`, чтение
и замену через индексатор, удаление по случайным индексам, сохранение вместимости
после удаления всех элементов и повторное использование массива. Сценарий также
показывает обнаружение изменений во время обхода и ошибки аргументов,
поиск по значению и позиции среди дубликатов, обнаружение записи из условия,
очистку и повторное использование после очистки.
Новый случайный прогон и повтор конкретного прогона:

```powershell
dotnet test Practice.DataStructures.sln --configuration Release --settings laboratory.runsettings --filter "FullyQualifiedName~DynamicArrayLaboratoryTests" --logger "console;verbosity=detailed"

dotnet test Practice.DataStructures.sln --configuration Release --settings laboratory.runsettings --filter "FullyQualifiedName~DynamicArrayLaboratoryTests" --logger "console;verbosity=detailed" --environment DATASTRUCTURES_LAB_SEED=12345
```

В первой команде подразумевается, что `DATASTRUCTURES_LAB_SEED` не задана в
окружении. Во второй заменить `12345` на seed из нужного вывода. Параметр
`--environment` действует для запуска тестов и не сохраняет seed в следующих
сеансах. В IDE ту же переменную можно задать в окружении лабораторного запуска.

## Запуск лабораторных сценариев и измерений

Помечайте диагностику `[Trait("Category", "Laboratory")]`, измерения —
`[Trait("Category", "Performance")]`. Для их запуска явно выберите
`laboratory.runsettings` без исключающего фильтра и укажите нужную категорию:

```powershell
dotnet test Practice.DataStructures.sln --configuration Release --settings laboratory.runsettings --filter "Category=Laboratory" --logger "console;verbosity=detailed"
dotnet test Practice.DataStructures.sln --configuration Release --settings laboratory.runsettings --filter "Category=Performance" --logger "console;verbosity=detailed"
```

Демонстрация `DynamicArray<T>` уже доступна в категории Laboratory.
Сценариев Performance пока нет; их запуск завершится ошибкой отсутствия тестов.

Лабораторный сценарий вызывает публичный API Core и проверяет результат.
Сохраняйте seed и параметры во входных данных или выводе согласно правилам
демонстрации и измерений выше. Нужные тесту данные держите рядом с его проверками; файловые данные
явно копируйте в output через csproj и загружайте относительно `AppContext.BaseDirectory`.
Не привязывайте сценарии к текущей рабочей папке или абсолютным локальным путям.

Для измерений: Release, запуск без отладчика, прогрев, повторные прогоны,
эквивалентные входы и проверка корректности до замера. Генерация данных и вывод
диагностик должны находиться вне измеряемого участка. Записывайте время,
аллокации, размер входа, seed и окружение. Не используйте абсолютные пороги
времени как критерий корректности. Измерения запускайте отдельно от обычных
тестов и отключайте параллельность для коллекции с измерительными сценариями.

## IDE

Откройте `Practice.DataStructures.sln` в Rider и используйте встроенный xUnit
runner. Для общего прогона настройте поддержку `.runsettings` и выберите файл
из корня решения; для лабораторной сессии выберите `laboratory.runsettings`
и нужную категорию. Применение VSTest-настроек зависит от runner IDE.
Если настройки фильтра IDE не применяются, исключите категории Laboratory и
Performance в обычной тестовой сессии и запускайте их отдельными сессиями.
CLI-команды выше задают единый воспроизводимый способ локального запуска.

Tests использует автоматически создаваемую точку входа xUnit v3.
Не добавляйте собственный `Program.cs` или учебное консольное меню.
