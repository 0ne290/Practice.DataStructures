Источник: [Практикум по программированию — инженерные задачи и спецификации](https://docs.google.com/document/d/1gc4Alrd9FbaK45gFsvVi9R8c1b2ZkauCpzki4IRLPGg/edit).
Локальная адаптация общих правил и раздела 4 от 30 октября 2026 года. Размещение репозитория на внешнем сервисе не требуется. Остальные дисциплины в этот репозиторий не входят.

## Организация исходного кода и тестовой лаборатории (общее правило)

Каждая дисциплина (раздел практикума) ведётся в отдельном Git-репозитории с одним C# solution (.sln или .slnx) и ровно двумя проектами: библиотекой классов `<Discipline>.Core` и проектом `<Discipline>.Tests`. Репозиторий дисциплины содержит все её задания, разделённые по папкам и пространствам имён. Не создавать отдельные репозитории или проекты для каждой задачи. Названия репозиториев и пространств имён фиксировать при создании дисциплины.

Целевая платформа задаётся в `Directory.Build.props`; версия C# выбирается SDK по целевой платформе. Версии установленных инструментов окружения не закрепляются: пользователь обновляет их самостоятельно, а нейросеть исследует фактическое окружение и ведёт исключённый из Git локальный кэш по правилам [работы с окружением](environment.md). Для тестов — xUnit.net v3, совместимые тестовые SDK и runner. Версии NuGet-зависимостей задаются в проекте и lock-файлах; обновление зависимостей сопровождается проверками совместимости. У xUnit нет собственного понятия «LTS».

`<Discipline>.Core` — только библиотека классов (OutputType Library), без Program.cs, Main, консольного меню, запускаемого приложения или учебного интерфейса. Здесь находятся исключительно решения практикума, их публичные контракты и необходимая внутренняя логика. Вся реализация Core выполняется автором практикума самостоятельно; нейросеть не пишет, не дополняет и не исправляет продукционный код Core без отдельного явного запроса. Исключение — разрешённые объяснения, ревью и постановка требований без готового решения.

`<Discipline>.Tests` ссылается на Core и является одновременно тестовым стендом и лабораторией. Нейросеть ставит задачу в академическом стиле: что реализовать, какие операции и сведения предоставить, где выбирать элементы по индексу, а где по условию. Не превращать постановку в полную спецификацию-ТЗ и не раскрывать заранее сигнатуры, инварианты, граничные случаи и ветки решения без запроса автора. Приведённые ниже критерии приёмки служат материалом для ревью, а не обязательным перечнем подсказок в начальной постановке.

Автор самостоятельно выбирает API и пишет реализацию. Нейросеть сначала проверяет только функциональную корректность и надёжность, включая инварианты и граничные случаи; автор исправляет обнаруженные проблемы. После завершения этого этапа отдельно проводится ревью архитектуры, чистоты кода и API с исправлениями автора. После обоих этапов нейросеть оформляет спецификацию принятого решения: XML-комментарии, тесты и полноценную лабораторную демонстрацию. Оформление XML-комментариев разрешено; изменение реализации, объявлений и сигнатур Core требует отдельного явного запроса. Актуальные намеренные решения автора имеют приоритет над исходной спецификацией. Подробный порядок работы и границы адаптации описаны в [тестовой лаборатории](testing.md).

Все обычные автоматические тесты оформляются в стиле AAA (Arrange / Act / Assert) с явно различимыми этапами, говорящими именами и независимыми проверками. Использовать [Fact] для одиночных сценариев, [Theory] для наборов входных данных; проверять штатные результаты, граничные случаи, ошибки, инварианты и детерминированность, где она предусмотрена. Нельзя заменять проверки печатью результата или считать успешный запуск доказательством корректности. Эталонные механизмы .NET допускаются в тестах, если их использование не подменяет исследуемый алгоритм в Core.

На каждую задачу сразу создавать ровно одну лабораторную точку запуска `[Fact]` категории Laboratory средствами xUnit / dotnet test и IDE test runner. До завершения обоих этапов ревью это полигон автора для самостоятельных экспериментов и отладки; не заменять и не дополнять его наработки без запроса. После ревью нейросеть заменяет содержимое полигона полноценной демонстрацией итогового решения. Итоговая демонстрация по умолчанию выбирает новый случайный seed, генерирует данные, вызывает публичный API Core, сверяет результаты и выводит понятный ход эксперимента через ITestOutputHelper (или стандартный механизм вывода используемой версии xUnit). До выполнения операций записывать seed и параметры; выводить входные данные и поддерживать явное задание seed для повторения прогона. Печать результатов и промежуточных состояний дополняет Assert. При расширении API использовать существующую точку запуска; сравнительные измерения производительности отделять от демонстрации. Обычные тесты остаются детерминированными, а для сравнительных измерений используются фиксированные seed и одинаковые входы.

Проверки производительности и ресурсоёмкости отделять от обычных unit-тестов (отдельные категории/traits и фильтры запуска); не использовать хрупкие абсолютные ограничения времени как критерий корректности. Для сравнительных измерений — прогрев, повторные прогоны, эквивалентные входы, контроль корректности до замера, исключение генерации входов из измеряемого участка и отчёт о времени/аллокациях. При необходимости BenchmarkDotNet может использоваться отдельно, но не должен навязывать третий проект или запуск в обычном тестовом прогоне; при его несовместимости с заданной структурой достаточно воспроизводимых диагностических замеров из Tests.

Один набор контрактных тестов по возможности применяется ко всем альтернативным реализациям одинаковой абстракции. При этом специфические внутренние инварианты и особенности реализации тестировать отдельными группами. Результат дисциплины считается принятым, когда Core собирается как библиотека, Tests выполняет проверки, а лабораторные сценарии запускаются по явному выбору без модификации Core.

## Раздел 4. Структуры данных, деревья и графовые алгоритмы

Источник: И. А. Красиков. «Структуры и алгоритмы обработки данных в ЭВМ», ТУСУР ФДО, 2016, 252 с. Это учебное пособие с теорией и примерами C, а не отдельная методичка вариантов программных работ. Ниже — наши инженерные постановки на основе материала книги, не оригинальные формулировки заданий. Основной язык реализации: C#. Приоритет — деревья и графы; простейшие структуры сохранены как факультативная база.

На втором этапе ревью обязательна проверка согласованности имени типа,

После обоих этапов итоговые XML-комментарии оформляются и сверяются по

## Семантика коллекций: API и организация хранения

Для всего практикума действует [словарь семантики коллекций](collection-semantics.md).
Список, стек, очередь и дек задают абстракцию и профиль API. Хранение на массиве
и хранение на связанных узлах описывают организацию хранения; односвязность
и двусвязность уточняют связи узлов. Политика вместимости, расширения API
и требования к сложности задаются отдельно. «Классический» и «традиционный»
означают один базовый профиль из словаря.

Встроенный массив C# (`T[]`) — стандартная базовая фундаментальная структура
данных фиксированной длины, предоставляемая языком и средой выполнения.
Собственную реализацию фиксированного массива не создавать. Все коллекции
с хранением на массивах строить на `T[]`, непосредственно или через собственные
коллекции проекта. Связные реализации строятся на узлах и ссылках.
Массив не является отдельным профилем API реализуемых коллекций.
Слово «линейный» не используется для обозначения хранения на массиве.

Имена типов, файлов и тестовых тем согласуются со
[словарём](collection-semantics.md#названия-и-принятые-варианты).
Обновление словаря само по себе не расширяет принятый API.

## Инженерное расширение раздела 4: два подхода к реализации структур данных

Принцип преемственности: собственные структуры используются другими через
композицию там, где это соответствует назначению и требуемой сложности.
Роль каждого слоя должна быть объяснена; отдельный класс не обязательно
представляет отдельный АТД. Общая техника хранения не означает одинаковый API.

Подходящие абстракции реализовывать на массивах (Array-based) и на связанных
узлах (Linked-based). Альтернативные реализации с одинаковым контрактом
должны проходить общие контрактные тесты. Специфические требования к стоимости
операций указывать для каждой реализации отдельно; сравнение времени
и аллокаций допускается как лабораторный эксперимент.
Общность абстракции списка не требует одинакового полного API и одинаковых
средств адресации у всех его реализаций.

Базовые собственные коллекции: `ArrayList<T>` — расширяемый список на `T[]`
с Count/Capacity; `SinglyLinkedList<T>` — список на односвязных узлах;
`DoublyLinkedList<T>` — список на двусвязных узлах. Они реализуются самостоятельно
и тестируются отдельно. Внутри учебных структур запрещено использовать готовые
`List<T>`, `LinkedList<T>`, `Stack<T>`, `Queue<T>` и прочие коллекции BCL
как хранилище. Разрешены `T[]`, примитивы языка и runtime, в том числе Array.Copy,
если цель задания не требует самостоятельно реализовать именно эту операцию.
Стандартные коллекции допустимы как эталоны в Tests.

Парные структуры: `ArrayStack<T>` / `LinkedStack<T>`,
`ArrayQueue<T>` / `LinkedQueue<T>` и `ArrayDeque<T>` / `LinkedDeque<T>`.
Очередь и дек — расширения практикума. Не навязывать двусвязный список стеку,
когда достаточно односвязных узлов. Собственные коллекции переиспользовать,
если сохраняется нужная асимптотика и не возникают искусственные зависимости.
Перед очередями и деками автор добавляет `Insert` в `ArrayList<T>` и реализует
`CircularArrayList<T>`. Согласованные операции, ограничения и стоимость приведены в
[профилях списков на массивах](array-list-profiles.md).

`ArrayQueue<T>` и `ArrayDeque<T>` строятся через композицию с собственным
`CircularArrayList<T>` и скрывают его полный позиционный API. Их связные
альтернативы используют односвязный и двусвязный списки соответственно.
Сигнатуры целевого API списков согласованы по запросу автора;
устройство реализации и алгоритмы остаются самостоятельной работой автора.

Деревья поиска и AVL реализовывать на собственных узлах; не требовать
искусственную вторую версию на массиве без осмысленного отдельного задания.
Для графов сравнивать матрицу и список смежности через общий контракт;
обходы и другие алгоритмы по возможности писать один раз поверх контракта.
Сортировки и численные процедуры не дублировать только ради двух способов
хранения: разделять представление данных и сам алгоритм.

Порядок изучения: `ArrayList<T>` → `SinglyLinkedList<T>` →
`DoublyLinkedList<T>` → парные стеки → расширение `ArrayList<T>` операцией
`Insert` → `CircularArrayList<T>` → парные очереди → парные деки →
деревья → графы и алгоритмы. Каждый этап сопровождается тестами корректности
и специфических инвариантов; тесты создаёт нейросеть, реализации Core — автор.
Это расширение относится к организации практикума и не приписывается
оригинальному учебному пособию.

Стеки и парные очереди завершены. Результаты ревью очередей и оформление
описаны в [тестовой лаборатории](testing.md#завершённое-упражнение-парные-очереди).
Парные деки также завершены: оба этапа ревью, XML-комментарии, общие
контрактные тесты и единая демонстрация оформлены. Результаты —
в [ревью LinkedDeque<T>](reviews/linked-deque.md) и
[тестовой лаборатории](testing.md#завершённое-упражнение-парные-деки).
Текущий статус двух списков отмечен в их целевом профиле.
Лабораторные полигоны создаются при начале соответствующих упражнений;
для расширения готовой структуры используется её существующий полигон.
Обе реализации каждой пары с одинаковым API должны соблюдать общий контракт;
тесты и демонстрации оформляются после двух этапов ревью.

После дек отдельных заданий по организации хранения этих списков в плане нет.
Дальнейшие алгоритмы используют готовые коллекции через их публичные контракты;
детали хранения остаются внутри реализаций.

## Выбор элементов по условию и по индексу

Для всех текущих и будущих коллекций применять выбор по условию к операциям,
которые по своей природе последовательно проверяют элементы. В академической
постановке использовать слово «условие»; в C# оно передаётся делегатом-предикатом.
Условие получает элемент, а в коллекциях с определённым порядком — также его
текущую позицию. Способ сравнения выбирает пользователь: по ссылке, полному
значению, отдельным полям или другим признакам, в том числе с использованием
других элементов коллекции. Конкретные сигнатуры и поведение выбирает автор.

В списке на массиве к таким операциям относятся поиск позиции (`IndexOf`)
и проверка наличия (`Contains`): их поиск должен поддерживать условие.
Индексатор и удаление по известному индексу сохраняются. Не заменять прямой
доступ за O(1) последовательным поиском и не требовать предикат от операции
только потому, что другая её часть содержит цикл (например, сдвиг при удалении).

В связных списках выбор произвольного элемента обычно требует прохода по узлам
и допускает условие. Это не означает, что все операции списка требуют перебора:
действия с известной головой или хвостом могут выполняться за O(1).
Не добавлять им поиск по условию без необходимости. Для деревьев, хеш-таблиц
и других будущих структур также сохранять специализированные способы доступа;
отсутствие массива само по себе не является основанием для перебора.

Этот раздел задаёт направление дальнейшей доработки API; текущее состояние
реализации и тестов описано в [тестовой лаборатории](testing.md).

## СА-01. Реализация и сравнение алгоритмов сортировки

Раздел 3, стр. 83–111. Цель: исследовать устойчивость, сложность и расход памяти различных стратегий сортировки. Реализовать пузырьковую (включая улучшенную), выбором, вставками, пирамидальную, слиянием, быструю и поразрядную сортировки; для каждой явно определить тип входных значений и правила сравнения. Контракт: массив входных элементов; результат — отсортированная последовательность и метрики сравнений, перемещений, дополнительной памяти и времени. Для поразрядной сортировки определить поддержку отрицательных чисел и разрядов. Приёмка: пустой и одноэлементный вход, уже упорядоченный и обратный порядок, дубликаты, одинаковые ключи с разными payload, большие случайные массивы; совпадение с эталонной сортировкой, проверка сохранения мультимножества элементов, документированная устойчивость каждого алгоритма.

## СА-02. Динамический список, двусвязный список и стек (базовый, необязательный)

Заголовок сохраняет обозначение темы исходной адаптации. В текущем словаре
«динамический» означает изменяемый размер и сам по себе не означает связность;
конкретные задания различают профиль API списка и организацию хранения
согласно [семантике коллекций](collection-semantics.md).

Раздел 4, стр. 112–180. Цель: разобраться в стоимости вставок, удаления и обходов, управлении ссылками и инвариантах. Реализовать контейнеры с добавлением, удалением, поиском, перечислением, очищением и проверкой корректности связей; отдельно поддержать LIFO-стек и вычисление арифметических выражений в обратной польской нотации. Приёмка: пустые контейнеры, операции с головой/хвостом, удаление единственного элемента, повторное добавление после очистки, переполнение/недостаток операндов ОПН, некорректные токены и деление на ноль. Стандартные коллекции .NET разрешены как эталон, но не как внутренняя реализация учебных структур.

## СА-03. Бинарное дерево поиска и АВЛ-дерево

Раздел 5, стр. 181–216. Цель: изучить упорядоченные и балансируемые структуры и их инварианты. Создать библиотеку бинарного дерева поиска с поиском, вставкой, удалением, обходами и политикой обработки равных ключей. Дополнительно реализовать AVL-вариант с автоматическим восстановлением баланса после модификаций. Контракт: набор операций с ключами; выход — результаты поиска, порядок обходов, высота/размер дерева, диагностические сведения о балансировке.

Критерии приёмки: вставка по возрастанию/убыванию, случайные ключи, дубликаты, удаление листа/узла с одним или двумя потомками/корня, поиск отсутствующего элемента, пустое дерево; после каждой операции верный порядок in-order, согласованность числа элементов, отсутствие циклов и потерянных узлов. AVL-инвариант: для каждого узла модуль разности высот поддеревьев не больше 1; измерить высоты и число сравнений для упорядоченных и случайных входов. Рекомендуемое расширение — поиск порядковой статистики, но не обязательное.

## СА-04. Представление графа и алгоритмы DFS/BFS

Разделы 6.1–6.3, стр. 217–231. Цель: разработать универсальную модель ориентированных/неориентированных, взвешенных/невзвешенных графов и два алгоритма обхода. Вход: множество вершин и рёбер, начальная вершина, выбранный способ представления (матрица смежности или список смежности). Выход: последовательность посещения, дерево обхода, достижимость и расстояния по числу рёбер для BFS. Согласовать поддержку кратных рёбер и петель, порядок соседей, возможность несвязности.

Приёмка: граф без рёбер, одна вершина, несвязные компоненты, циклы, петли, изолированные вершины, направленные связи, повторные рёбра; каждая достижимая вершина посещена один раз, недостижимые не ошибочно отмечены; BFS выдаёт минимальное число рёбер от старта, DFS соблюдает правила обхода при фиксированном порядке соседей. Сравнить затраты памяти и времени матрицы и списков.

## СА-05. Минимальное остовное дерево: Прим и Крускал

Раздел 6.4, стр. 232–237. Цель: построить минимальный остов взвешенного неориентированного графа. Реализовать оба алгоритма независимо на одном формате входа; вернуть рёбра остова, полную стоимость, количество покрытых вершин, статус связности. Для несвязного графа явно выбрать и задокументировать: отказ или минимальный остовный лес. Допустить равные и отрицательные веса, если они корректны для принятой модели.

Приёмка: одиночная вершина, дерево без лишних рёбер, граф с циклами, равные веса и несколько оптимальных остовов, отрицательные веса, несвязные компоненты, параллельные рёбра. Проверка: для связного графа n−1 ребро, отсутствуют циклы, достигнуты все вершины, вес совпадает у Прима и Крускала (на одном графе), независимо от возможного различия конкретных рёбер.

## СА-06. Эйлеровы и гамильтоновы циклы

Разделы 6.5–6.6, стр. 238–239. Цель: понять различие между обходом всех рёбер ровно один раз и посещением всех вершин ровно один раз. Создать два независимых инструмента: обнаружение существования и построение эйлерова цикла; поиск гамильтонова цикла для ограниченного размера графа с отчётностью о неуспехе. Указать ориентированность, допустимость параллельных рёбер и петель, стратегию отсечения перебора для сложного случая.

Приёмка: простой цикл, путь без замыкания, несвязный граф, мосты, петли и кратные рёбра (если поддерживаются), полный и разреженный граф. Эйлеров результат использует каждое ребро нужное количество раз и возвращается в начало; гамильтонов посещает каждую вершину ровно раз до замыкающего перехода. Для гамильтонова поиска корректно различать «цикла не существует» и «поиск ограничен лимитом ресурсов».

## СА-07. Кратчайшие пути в графе

Раздел 6.7, стр. 240–244. Цель: вычислять минимальную стоимость пути между вершинами и отличать достижимость от оптимальности. Вход: граф, веса, начальная/целевая вершины; выход: стоимость и восстановленная последовательность вершин/рёбер либо статус недостижимости. Конкретный алгоритм выбирать по свойствам весов, разбираемым в пособии; запрещать использовать вариант для неотрицательных весов на отрицательных рёбрах без явной диагностики. Приёмка: изолированные вершины, прямое/обходное ребро, одинаковые по стоимости маршруты, старт=финиш, циклы, нулевые веса, несвязность; стоимость восстановленного пути обязана совпадать с найденной оценкой.

## СА-08. Сравнительное исследование деревьев и графовых алгоритмов

Наше интеграционное расширение. Построить генератор воспроизводимых тестовых данных и измерительный стенд для СА-03…СА-07. Фиксировать seed, масштаб входа, плотность графа, веса, форму дерева, число операций, время и память. Ожидаемый результат — не «универсально лучший алгоритм», а обоснованное объяснение различий алгоритмов для разных классов входов. Обязательна проверка корректности результатов перед сравнением скорости; тесты не должны смешивать генерацию данных с измеряемой операцией.
