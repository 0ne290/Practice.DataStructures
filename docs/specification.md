# Спецификация практикума

Источник: [Практикум по программированию — инженерные задачи и спецификации](https://docs.google.com/document/d/1gc4Alrd9FbaK45gFsvVi9R8c1b2ZkauCpzki4IRLPGg/edit).
Локальная адаптация общих правил и раздела 4 от 30 октября 2026 года. Размещение репозитория на внешнем сервисе не требуется. Остальные дисциплины в этот репозиторий не входят.

## Организация исходного кода и тестовой лаборатории (общее правило)

Каждая дисциплина (раздел практикума) ведётся в отдельном Git-репозитории с одним C# solution (.sln или .slnx) и ровно двумя проектами: библиотекой классов `<Discipline>.Core` и проектом `<Discipline>.Tests`. Репозиторий дисциплины содержит все её задания, разделённые по папкам и пространствам имён. Не создавать отдельные репозитории или проекты для каждой задачи. Названия репозиториев и пространств имён фиксировать при создании дисциплины.

Технологический стек: последняя стабильная LTS-версия .NET и соответствующая ей стабильная версия C#; по состоянию на октябрь 2026 года — .NET 10 LTS / C# 14. Для тестов — актуальная стабильная xUnit.net v3 (на эту дату xunit.v3 4.0.2), совместимые тестовые SDK и runner. Обновления мажорных версий проводить осознанно; фиксировать SDK через global.json и версии NuGet-пакетов в репозитории. У xUnit нет собственного понятия «LTS»; выбирать последнюю стабильную поддерживаемую ветку, а не предполагать статус LTS.

`<Discipline>.Core` — только библиотека классов (OutputType Library), без Program.cs, Main, консольного меню, запускаемого приложения или учебного интерфейса. Здесь находятся исключительно решения практикума, их публичные контракты и необходимая внутренняя логика. Вся реализация Core выполняется автором практикума самостоятельно; нейросеть не пишет, не дополняет и не исправляет продукционный код Core без отдельного явного запроса. Исключение — разрешённые объяснения, ревью и постановка требований без готового решения.

`<Discipline>.Tests` ссылается на Core и является одновременно тестовым стендом и лабораторией: нейросеть пишет и поддерживает тесты, тестовые данные, фикстуры, проверки инвариантов, диагностические запуски и измерительные сценарии. Тесты должны проверять внешне наблюдаемый контракт, а не выдуманные детали реализации; если API ещё не определён, сначала согласовать минимальный контракт или адаптировать тесты к уже реализованному API без переписывания Core.

Все обычные автоматические тесты оформляются в стиле AAA (Arrange / Act / Assert) с явно различимыми этапами, говорящими именами и независимыми проверками. Использовать [Fact] для одиночных сценариев, [Theory] для наборов входных данных; проверять штатные результаты, граничные случаи, ошибки, инварианты и детерминированность, где она предусмотрена. Нельзя заменять проверки печатью результата или считать успешный запуск доказательством корректности. Эталонные механизмы .NET допускаются в тестах, если их использование не подменяет исследуемый алгоритм в Core.

Лабораторные сценарии запускаются средствами xUnit / dotnet test и IDE test runner: генерируют воспроизводимые входные данные, вызывают публичный API Core, сверяют результаты и при необходимости записывают человекочитаемые диагностики через ITestOutputHelper (или стандартный механизм вывода используемой версии xUnit). Печать результатов, промежуточных состояний и метрик допустима дополнительно к Assert. Обязательно сохранять seed и параметры сценария, если данные генерируются.

Проверки производительности и ресурсоёмкости отделять от обычных unit-тестов (отдельные категории/traits и фильтры запуска); не использовать хрупкие абсолютные ограничения времени как критерий корректности. Для сравнительных измерений — прогрев, повторные прогоны, эквивалентные входы, контроль корректности до замера, исключение генерации входов из измеряемого участка и отчёт о времени/аллокациях. При необходимости BenchmarkDotNet может использоваться отдельно, но не должен навязывать третий проект или запуск в обычном тестовом прогоне; при его несовместимости с заданной структурой достаточно воспроизводимых диагностических замеров из Tests.

Один набор контрактных тестов по возможности применяется ко всем альтернативным реализациям одинаковой абстракции. При этом специфические внутренние инварианты и особенности реализации тестировать отдельными группами. Результат дисциплины считается принятым, когда Core собирается как библиотека, Tests выполняет проверки, а лабораторные сценарии запускаются по явному выбору без модификации Core.

## Раздел 4. Структуры данных, деревья и графовые алгоритмы

Источник: И. А. Красиков. «Структуры и алгоритмы обработки данных в ЭВМ», ТУСУР ФДО, 2016, 252 с. Это учебное пособие с теорией и примерами C, а не отдельная методичка вариантов программных работ. Ниже — наши инженерные постановки на основе материала книги, не оригинальные формулировки заданий. Основной язык реализации: C#. Приоритет — деревья и графы; простейшие структуры сохранены как факультативная база.

## Инженерное расширение раздела 4: два подхода к реализации структур данных

Реализовывать подходящие абстрактные структуры двумя независимыми способами: Array-based (последовательное хранение) и Linked-based (связанные узлы). Обе реализации должны соблюдать один публичный контракт и проходить одинаковые контрактные тесты; дополнительное сравнение времени и аллокаций допускается как лабораторный эксперимент, а не вместо проверки корректности.

Базовые собственные механизмы: `DynamicArray<T>` (массив T[], Count/Capacity, рост ёмкости), `SinglyLinkedList<T>` (голова, хвост, Next) и `DoublyLinkedList<T>` (Previous/Next, инварианты прямой и обратной связности). Они реализуются самостоятельно и тестируются отдельно. Внутри учебных структур запрещено использовать готовые `List<T>`, `LinkedList<T>`, `Stack<T>`, `Queue<T>` и прочие коллекции BCL как хранилище; разрешены T[], примитивы языка и runtime, в том числе Array.Copy, если цель задания не требует самостоятельно реализовать именно эту операцию. Стандартные коллекции допустимы как эталоны в Tests.

Рекомендуемые парные структуры: `ArrayStack<T>`/`LinkedStack<T>` и `ArrayQueue<T>`/`LinkedQueue<T>` (очередь — расширение практикума). Не навязывать двусвязный список стеку, когда достаточно односвязных узлов. Для очереди на массиве использовать кольцевую организацию, не удалять каждый раз первый элемент со сдвигом всего массива. Переиспользовать собственные примитивы там, где это не ухудшает асимптотику и не создаёт искусственных зависимостей.

Деревья поиска и AVL реализовывать на собственных узлах; не требовать искусственную вторую версию на массиве, если это не является осмысленным отдельным заданием. Для графов сравнивать два представления — матрицу и список смежности — через общий контракт, а обходы и прочие алгоритмы по возможности писать один раз поверх контракта. Алгоритмы сортировки и численные процедуры не нужно дублировать только ради двух стилей хранения: разделять представление данных и сам алгоритм.

Порядок изучения: `DynamicArray<T>` → `SinglyLinkedList<T>` → `DoublyLinkedList<T>` → парные стеки → парные очереди → деревья → графы и алгоритмы. Каждый этап сопровождается собственными тестами корректности и инвариантов; тесты создаёт нейросеть, реализации Core — автор практикума. Это расширение относится к организации практикума и не приписывается оригинальному учебному пособию.

## СА-01. Реализация и сравнение алгоритмов сортировки

Раздел 3, стр. 83–111. Цель: исследовать устойчивость, сложность и расход памяти различных стратегий сортировки. Реализовать пузырьковую (включая улучшенную), выбором, вставками, пирамидальную, слиянием, быструю и поразрядную сортировки; для каждой явно определить тип входных значений и правила сравнения. Контракт: массив входных элементов; результат — отсортированная последовательность и метрики сравнений, перемещений, дополнительной памяти и времени. Для поразрядной сортировки определить поддержку отрицательных чисел и разрядов. Приёмка: пустой и одноэлементный вход, уже упорядоченный и обратный порядок, дубликаты, одинаковые ключи с разными payload, большие случайные массивы; совпадение с эталонной сортировкой, проверка сохранения мультимножества элементов, документированная устойчивость каждого алгоритма.

## СА-02. Динамический список, двусвязный список и стек (базовый, необязательный)

Раздел 4, стр. 112–180. Цель: разобраться в стоимости вставок, удаления и обходов, управлении ссылками и инвариантах. Реализовать контейнеры с добавлением, удалением, поиском, перечислением, очищением и проверкой корректности связей; отдельно поддержать LIFO-стек и вычисление арифметических выражений в обратной польской нотации. Приёмка: пустые контейнеры, операции с головой/хвостом, удаление единственного элемента, повторное добавление после очистки, переполнение/недостаток операндов ОПН, некорректные токены и деление на ноль. Стандартные коллекции .NET разрешены как эталон, но не как внутренняя реализация учебных структур.

## СА-03. Бинарное дерево поиска и АВЛ-дерево

Раздел 5, стр. 181–216. Цель: изучить упорядоченные и балансируемые структуры и их инварианты. Создать библиотеку бинарного дерева поиска с поиском, вставкой, удалением, обходами и политикой обработки равных ключей. Дополнительно реализовать AVL-вариант с автоматическим восстановлением баланса после модификаций. Контракт: набор операций с ключами; выход — результаты поиска, порядок обходов, высота/размер дерева, диагностические сведения о балансировке.

Критерии приёмки: вставка по возрастанию/убыванию, случайные ключи, дубликаты, удаление листа/узла с одним или двумя потомками/корня, поиск отсутствующего элемента, пустое дерево; после каждой операции верный порядок in-order, согласованность числа элементов, отсутствие циклов и потерянных узлов. AVL-инвариант: для каждого узла модуль разности высот поддеревьев не больше 1; измерить высоты и число сравнений для упорядоченных и случайных входов. Рекомендуемое расширение — поиск порядковой статистики, но не обязательное.

## СА-04. Представление графа и алгоритмы DFS/BFS

Разделы 6.1–6.3, стр. 217–231. Цель: разработать универсальную модель ориентированных/неориентированных, взвешенных/невзвешенных графов и два алгоритма обхода. Вход: множество вершин и рёбер, начальная вершина, выбранный способ представления (матрица смежности или список смежности). Выход: последовательность посещения, дерево обхода, достижимость и расстояния по числу рёбер для BFS. Согласовать поддержку кратных рёбер и петель, порядок соседей, возможность несвязности.

Приёмка: граф без рёбер, одна вершина, несвязные компоненты, циклы, петли, изолированные вершины, направленные связи, повторные рёбра; каждая достижимая вершина посещена один раз, недостижимые не ошибочно отмечены; BFS выдаёт минимальное число рёбер от старта, DFS соблюдает правила обхода при фиксированном порядке соседей. Сравнить затраты памяти и времени матрицы и списков.

## СА-05. Минимальное остовное дерево: Прим и Крускал

Раздел 6.4, стр. 232–237. Цель: построить минимальный остов взвешенного неориентированного графа. Реализовать оба алгоритма независимо на одном формате входа; вернуть рёбра остова, полную стоимость, количество покрытых вершин, статус связности. Для несвязного графа явно выбрать и задокументировать: отказ или минимальный остовный лес. Допустить равные и отрицательные веса, если они корректны для принятой модели.

Приёмка: одиночная вершина, дерево без лишних рёбер, граф с циклами, равные веса и несколько оптимальных остовов, отрицательные веса, несвязные компоненты, параллельные рёбра. Проверка: для связного графа n−1 ребро, отсутствуют циклы, достигнуты все вершины, вес совпадает у Прима и Крускала (на одном графе), независимо от возможного различия конкретных рёбер.

## СА-06. Эйлеровы и гамильтоновы циклы

Разделы 6.5–6.6, стр. 238–239. Цель: понять различие между обходом всех рёбер ровно один раз и посещением всех вершин ровно один раз. Создать два независимых инструмента: обнаружение существования и построение эйлерова цикла; поиск гамильтонова цикла для ограниченного размера графа с отчётностью о неуспехе. Указать ориентированность, допустимость параллельных рёбер и петель, стратегию отсечения перебора для сложного случая.

Приёмка: простой цикл, путь без замыкания, несвязный граф, мосты, петли и кратные рёбра (если поддерживаются), полный и разреженный граф. Эйлеров результат использует каждое ребро нужное количество раз и возвращается в начало; гамильтонов посещает каждую вершину ровно раз до замыкающего перехода. Для гамильтонова поиска корректно различать «цикла не существует» и «поиск ограничен лимитом ресурсов».

## СА-07. Кратчайшие пути в графе

Раздел 6.7, стр. 240–244. Цель: вычислять минимальную стоимость пути между вершинами и отличать достижимость от оптимальности. Вход: граф, веса, начальная/целевая вершины; выход: стоимость и восстановленная последовательность вершин/рёбер либо статус недостижимости. Конкретный алгоритм выбирать по свойствам весов, разбираемым в пособии; запрещать использовать вариант для неотрицательных весов на отрицательных рёбрах без явной диагностики. Приёмка: изолированные вершины, прямое/обходное ребро, одинаковые по стоимости маршруты, старт=финиш, циклы, нулевые веса, несвязность; стоимость восстановленного пути обязана совпадать с найденной оценкой.

## СА-08. Сравнительное исследование деревьев и графовых алгоритмов

Наше интеграционное расширение. Построить генератор воспроизводимых тестовых данных и измерительный стенд для СА-03…СА-07. Фиксировать seed, масштаб входа, плотность графа, веса, форму дерева, число операций, время и память. Ожидаемый результат — не «универсально лучший алгоритм», а обоснованное объяснение различий алгоритмов для разных классов входов. Обязательна проверка корректности результатов перед сравнением скорости; тесты не должны смешивать генерацию данных с измеряемой операцией.

## Отдельная связанная задача — венгерский алгоритм (не из этого пособия)

В учебном пособии Красикова венгерский алгоритм и оптимальное назначение в двудольном графе не обнаружены. Он также не фигурировал как основное задание в трёх ранее разобранных методичках. Его логично добавлять из методички по методам оптимизации/исследованию операций, когда она будет предоставлена. Не приписывать текущему источнику.
